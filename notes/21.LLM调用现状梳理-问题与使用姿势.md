# LLM 调用现状梳理：问题与使用姿势

> **文档定位**：记录 enhance pipeline 中所有 LLM 调用点的现状、存在问题、使用姿势，作为改造方案（notes/22）的事实基础。
> **文档编号**：21
> **创建日期**：2026-04-24
> **关联文档**：notes/20（重构方案），notes/22（LLMClient 改造方案）

---

## 1. 整体调用地图

enhance pipeline 共 7 个 Stage，其中 3 个 Stage 调用 LLM，其余为纯规则/计算：

```
Stage 1: BlockIndexer        → 无 LLM（纯规则扫描，产出 TitleItem[] + BodyItem[]）
Stage 2: LLMSectionPlanner   → ✅ LLM 调用 #1（结构规划）
Stage 3: TokenEstimation     → 无 LLM（纯 token 计算）
Stage 4: SectionEnhance      → ✅ LLM 调用 #2（内容增强，多次）
Stage 5: DocEnhance          → ✅ LLM 调用 #3（全文汇总，多次）
Stage 6: ValidateStage       → 无 LLM
Stage 7: ComposeStage        → 无 LLM
```

---

## 2. 调用 #1：LLMSectionPlanner（Stage 2）

### 2.1 职责

将 BlockIndexer 产出的 `TitleItem[]` + `BodyItem[]` 语义分组，决定"哪些相邻标题合并为一个 EnhanceUnit"。

### 2.2 输入结构

构建 4 列 flat table 发给 LLM：

```
type      | "text/preview"   | chars | refs
title[00] | "1. 引言"        | 4     | 1,2,title
body      | "本文研究…"      | 160   | 1,3,paragraph
title[01] | "2. 方法"        | 4     | 2,1,title
body      | "我们提出…"      | 160   | 2,2,paragraph
```

**关键点**：body 行只发 **preview（最多 160 字符）**，不发完整正文。因此输入大小是 `O(标题数 × 200字符)`，与文档正文长度无关。

### 2.3 输出结构

```json
{
  "doc_type": "标准|论文|手册|法规|报告|其他",
  "sections": [
    {"seq_ids": [0, 1, 2], "title": "合并后的标题", "rationale": "分组理由"}
  ]
}
```

### 2.4 重试机制

最多 3 次 LLM 调用：
- 第 1 次：正常请求
- 第 2 次（失败后）：prompt 末尾追加"seq_ids 必须连续"约束
- 第 3 次（再失败）：prompt 末尾追加更强的"强制要求"说明

三次均失败 → fallback：每个 TitleItem 独立成节，不调 LLM。

### 2.5 上下文超限处理

当 `sys_tokens + user_tokens + output_reserve > available_input_tokens` 时，**直接 fallback，不调 LLM**。

### 2.6 当前问题

| 问题 | 影响 | 严重度 |
|------|------|--------|
| 超限直接 fallback，放弃语义分组 | 文档分段质量下降（每个 title 独立成节） | 低（输入已是 preview，真正超限很少发生） |
| 无 max_tokens 约束 | LLM 输出超长时 json.loads 静默截断失败 | 中 |
| JSON 无代码块清洗 | 模型返回 ````json...```` 时直接报错 | **高（P0）** |
| litellm http_retries 参数未生效 | HTTP 层无真正重试，只靠应用层 3 次 LLM 重试兜底 | 中 |

## 3. 调用 #2：SectionEnhanceStage（Stage 4）

### 3.1 职责

对每个 `EnhanceUnit` 的正文调 LLM，产出结构化增强字段：`{summary, keywords, main_idea, questions}`。

### 3.2 section 结构说明

**当前 EnhanceUnit 是完全 flat 的，无树结构，无层级**。旧的 `SectionNode` 树结构（level 0/1/2/3）已在 notes/20 重构中废弃。

每个 EnhanceUnit 的 `body_text` 是 LLM Section Planner 分组后该单元内所有标题+正文的拼接，长度不定。

### 3.3 三种调度模式

#### Mode A：全量单次 batch（最优路径）

触发条件：所有 section 合并后 tokens ≤ 90% 可用上下文。

```
所有 EnhanceUnit → 拼接成一个 sections_block → 单次 LLM 调用
返回：{section_id: {summary, keywords, main_idea, questions}, ...}
```

一次 API 调用处理所有 section，最高效。

#### Mode B：FFD 装箱 + 并发 batch

触发条件：总量超过 90% 上下文，但可以分箱装。

```
按 token 用量对 section 降序排列
贪心 FFD 装箱：每箱 token 总量 ≤ available_input_tokens
每箱作为一次 LLM 调用
ThreadPoolExecutor(max_workers=concurrency) 并发执行所有箱
```

batch 内失败 → 拆成逐 section 单独调用。

#### Mode C：超长单节 map-reduce

触发条件：单个 section 的 `body_text` > `single_section_budget`。

```
超长 body_text
    ↓ split_text_by_token_budget()（按段落边界切）
chunk_0, chunk_1, ..., chunk_N
    ↓ 各 chunk 独立调 _enhance_single_via_prompt()
    ↓ 产出 {summary_0, keywords_0, ...}, {summary_1, keywords_1, ...}, ...
    ↓ 拼接 chunk_summaries + chunk_main_ideas → merged_text
    ↓ 再调一次 _enhance_single_via_prompt(section_text=merged_text)
最终 {summary, keywords, main_idea, questions}
```

### 3.4 当前问题

| 问题 | 影响 | 严重度 |
|------|------|--------|
| JSON 无代码块清洗 | 同上，P0 故障 | **高** |
| max_tokens 未传 | batch 输出截断 → json.loads 失败 | 中 |
| Mode C merge 时丢弃 chunk keywords | 最终 keywords 完全由 merged_text 重新生成，可能漂移 | 低 |
| Mode C merge 无递归 | 极端情况（单节 20 万字）merge 输入仍可能过长 | 低（极端场景） |
| batch 失败降级为 single 时无 max_tokens | 同上 | 中 |

### 3.5 关于 batch 请求的必要性

有两种 batch 概念：
- **内容 batch（Mode A/B）**：多个 section 塞进一次 LLM 调用，LLM 一次性返回所有结果。**必须保留**，直接减少 API 调用次数。
- **并发执行**：多个 LLM 请求用 ThreadPoolExecutor 并行发出。**可以保留**，也可改为 litellm batch_completion，功能相同。

## 4. 调用 #3：DocEnhanceStage（Stage 5）

### 4.1 职责

以所有 section 增强结果为输入，产出全文级汇总：`{global_summary, global_keywords, doc_outline_insights, answerable_questions}`。

输入是 section 结果的 JSON（已压缩），**不是原始文档正文**，自然比较紧凑：

```
50 sections × 平均 700 字符/section ≈ 35000 字符 ≈ 8750 tokens
+ prompt overhead ≈ 总共约 12000 tokens
→ 对 32K+ 模型无压力，8K 模型 + 100 sections 才触发 Mode B
```

### 4.2 两种模式

#### Mode A：单次请求

触发条件：所有 section results JSON ≤ 90% 可用上下文。

```
section_results JSON → doc_summary.j2 prompt → 单次 LLM 调用
返回：{global_summary, global_keywords, doc_outline_insights, answerable_questions}
```

#### Mode B：2 级 map-reduce

触发条件：section results 总量超出单次请求上限。

```
section_results 按 token 分组
    ↓ 每组 → local_prompt → LLM → local_payload（local_summary 等）
    ↓ 所有 local_payloads → global_prompt → LLM → final global payload
```

### 4.3 质量重试机制（最多 4 次额外 LLM 调用）

每次 `_generate_doc_payload()` 调用后，顺序检测并按需重试：

| 检测项 | 触发条件 | 重试动作 |
|--------|---------|---------|
| 标题退化 | `doc_outline_insights` 内容像是标题列表 | prompt 追加"禁止复述标题"约束 |
| summary 退化 | `doc_outline_insights` 像是 section summaries 的抄袭 | prompt 追加"跨章节抽象洞察"要求 |
| 密度不足 | insights 数量 < 目标值（`min(max(n*2, 4), 22)`） | prompt 追加"至少 N 条"要求 |
| 同质化 | ≥60% insights 包含固定套话模板 | prompt 追加多角度维度提示 |

### 4.4 当前问题

| 问题 | 影响 | 严重度 |
|------|------|--------|
| JSON 无代码块清洗 | 同上，P0 | **高** |
| max_tokens 未传（5 处调用全未传） | 输出截断 → 静默失败 | 中 |
| Mode B reduce 阶段跨组信息丢失 | global 阶段看不到其他组的 sections，insights 无法捕捉跨组关系 | 中 |
| Mode B "摘要的摘要" | global_summary 基于 local_summaries，可能过度抽象 | 低 |

## 5. 当前 provider.py 的系统性问题

所有 LLM 调用最终都通过 `OpenAICompatibleProvider.generate_json()` 发出，该类存在以下根本缺陷：

### 5.1 双路径架构混乱

```python
def _chat_json(self, system_prompt, user_prompt):
    try:
        from litellm import completion     # litellm 路径
        response = completion(...)
        return json.loads(content)         # ← 裸 json.loads，无清洗
    except ModuleNotFoundError:
        # urllib 路径
        ...
```

- litellm 路径只 catch `ModuleNotFoundError`，其他任何异常（网络错误、超时、解析失败）都直接抛出，不经过任何 retry
- `http_retries` 参数只在 urllib 路径生效，litellm 路径的 `num_retries` 从未传入
- 实际上 litellm 已安装，urllib 路径**永远不会触发**——相当于 70+ 行代码从未执行

### 5.2 JSON 裸解析（P0 故障）

```python
return json.loads(content)  # ← 无代码块清洗
```

部分模型（即使开了 response_format json_object）仍会在回复中包裹 ` ```json\n...\n``` `，直接导致 `JSONDecodeError`。这是当前最高频的故障原因。

### 5.3 无 max_tokens 约束

三个调用场景（SectionPlan、SectionEnhance、DocEnhance）全部未传 `max_tokens`，导致：
- 批量 section 增强输出超长时被截断
- 截断后 `json.loads` 静默失败，section 标记为 `failed`

### 5.4 context_window 重复解析

`pipeline.py` 在 Stage 2 前解析一次（L78），Stage 3 `run_token_estimation_stage()` 内又解析一次（L45），两次解析逻辑相同，造成重复 I/O 和日志混乱。

### 5.5 无 fallback 模型支持

单一模型失败即整个 pipeline 失败，没有备用模型切换能力。

## 6. 问题优先级汇总

| 编号 | 问题 | 优先级 | 涉及文件 |
|------|------|--------|---------|
| P0-1 | JSON 代码块清洗缺失，LLM 返回 ` ```json``` ` 时直接崩溃 | **P0** | provider.py |
| P0-2 | litellm 路径只 catch ModuleNotFoundError，retry 机制失效 | **P0** | provider.py |
| P1-1 | max_tokens 未传，batch 输出被截断后静默失败 | P1 | process_steps/step_4_section_enhance.py / process_steps/step_5_doc_enhance.py / process_steps/step_2_section_plan.py |
| P1-2 | 无 fallback 模型支持，主模型宕机即 pipeline 失败 | P1 | provider.py / custom_config_loader.py |
| P2-1 | context_window 重复解析（pipeline.py Stage2 前 + TokenEstimation Stage3） | P2 | pipeline.py / process_steps/step_3_token_estimation.py |
| P2-2 | Mode C merge 时 keywords 丢失 | P2 | process_steps/step_4_section_enhance.py |
| P2-3 | DocEnhance Mode B 跨组 insights 质量损失 | P2 | process_steps/step_5_doc_enhance.py |
| P2-4 | SectionPlan 超限直接 fallback，未尝试分窗口规划 | P2 | process_steps/step_2_section_plan.py |
