## 1. MVP 边界决策（不做什么）

以下决策在 MVP 阶段确认，至今有效。扩展需单独开新版本文档。

| 编号 | 决策 | 理由 |
|------|------|------|
| D-01 | **不做 NormalizeStage**（不做中间产物重映射） | MVP 直接基于 `middle_json + content_list_v2` 原始产物处理，避免过度工程化 |
| D-02 | **不做 QA 生成**（`qa_pairs`） | 延后到 Phase 2，先跑稳文本增强链路 |
| D-03 | **不做图像/表格多模态增强执行** | 延后到 Phase 2，仅预留接口思想（见 notes/10 §5.2） |
| D-04 | **不做多模型路由** | 单 provider 足够 MVP 使用 |
| D-05 | **不引入向量库/知识图谱** | 不做 LightRAG 的重量级部分，只借鉴"先切块再处理"思想 |
| D-06 | **不恢复原始 md 单独输出** | 最终目录只有一份增强版 `{name}.md` |
| D-07 | **不做 `evidence_refs` + `confidence` 字段** | 延后到 Phase 2 质量护栏阶段 |
| D-08 | **不做缓存** | 延后到 Phase 2 |

## 2. 实际落地概况

### 2.1 Pipeline（8 阶段）

| # | Stage | 文件 | 职责 |
|---|-------|------|------|
| 1 | InputStage | `stages_input.py` | 校验 `middle_json` + `content_list_v2` 非空 |
| 2 | SectionBuildStage | `stages_section_build.py` | `content_list_v2` 扁平 blocks → `SectionNode` 层级树（纯规则，零 LLM，12 种编号 heuristic） |
| 2b | **SectionPlanStage** | `stages_section_plan.py` | LLM 驱动的自适应 Section 规划：碎片率检测 → 结构摘要 → LLM 分组 → 三层校验 → EnhanceUnit tree |
| 3 | TokenEstimationStage | `stages_token_estimation.py` | 五层 fallback 获取 context_window + 递归计算 estimated_tokens/subtree_tokens |
| 4 | SectionEnhanceStage | `stages_section_enhance.py` | 叶子→父节点 bottom-up 增强。Mode A（全量单批）/ B（FFD 装箱并发）/ C（超长 map-reduce） |
| 5 | DocEnhanceStage | `stages_doc_enhance.py` | 消费 L1 节点结果，生成 `global_summary` / `global_keywords` / `doc_outline_insights` + 3 层退化检测 |
| 6 | ValidateStage | `stages_validate.py` | schema + 内容 + 引用三类校验 |
| 7 | ComposeStage | `stages_compose.py` | `<enhance>` 标签插入 markdown |

技术规格：`notes/13`（Stage 2）、`notes/14`（Stage 3/4/5/6/7）、`notes/19`（Stage 2b）

### 2.3 输出产物

| 文件 | 说明 |
|------|------|
| `{name}_enhance.json` | 结构化增强结果（overview + sections，indent=2） |
| `{name}.md` | 增强版 Markdown（含 `<enhance>` 标签，唯一 md） |

格式规格见 `notes/14` §7。

### 2.3.1 新增：只获取 Markdown 的轻量交付路径（API + CLI）

在“客户只需要最终增强版 Markdown”场景下，增加了端到端的轻量交付能力：

- **API**：`GET /tasks/{task_id}/md?file_name=<stem>`
  - 返回 `text/markdown; charset=utf-8` 文件流
  - 避免下载 zip/解压，适合跨网与 Windows 侧直接保存
- **CLI**：`razel-mineru --md-only`
  - 任务完成后直接拉取 md 文件流并写入 `-o` 目录
  - 若服务端版本较旧（/md 返回 404/405），CLI 自动回退下载 `/result` zip，但 zip 中也只包含 md，客户端只提取 md 落盘

### 2.4 Provider

- 唯一实现：`OpenAICompatibleProvider`
- LLM 调用：litellm 优先，无 litellm 时 fallback 到原生 urllib HTTP
- Token 计数：`TokenCounter`（HuggingFace `AutoTokenizer` 优先，粗估兜底）
- 重试：429/5xx 自动 retry
- **未使用**：`tenacity`、`tiktoken`（原规划建议但实际未引入）

## 3. 原 MVP 规划 vs 实际落地差异

| 维度 | 原 MVP 规划（notes/11 原文） | 实际落地 | 说明 |
|------|---------------------------|---------|------|
| Pipeline 阶段数 | 6 阶段 | **8 阶段** | 新增 TokenEstimationStage + SectionPlanStage |
| Section 结构 | 扁平 `sections[]` | **层级 `SectionNode` tree** | notes/13 方案，支持多级嵌套 |
| Section 切分 | 标题块 + 字数阈值兜底 | **12 种编号 heuristic + 标题栈建树** | 完全不信任 raw_level |
| 增强调度 | 简单并发 + map-reduce lite | **三模式自适应（A/B/C）+ FFD 装箱 + bottom-up 父节点汇聚** | notes/14 方案 |
| Provider 实现 | 3 个 provider（openai/qwen/local） | **1 个 `OpenAICompatibleProvider`** | litellm 优先 + urllib fallback，足够覆盖 |
| 依赖库 | `litellm` + `tenacity` + `tiktoken` | **`transformers` + `pydantic` + `jinja2`** | 更轻量，无额外重型依赖 |
| Token 计数 | `tiktoken`（或同类） | **HuggingFace `AutoTokenizer`**（精确优先，粗估兜底） | 与 model_reference 对齐 |
| 输出 key 策略 | 隐含有映射层 | **全链路原生标准 key，无映射层** | notes/14 §7 |
| `doc_outline_insights` | "可选" | **必做**，含 `{text, section_id}` + 密度门控 + 退化检测 | notes/15 契约 |
| Prompt 模板 | 3 个（section/doc/keyword） | **4 个**（增加 `section_batch_summary.j2`） | 支持 batch 模式 |
| 代码目录 | `mineru/enhance/` | **`mineru/custom/enhance_mvp/`** | 放在 custom 下便于维护 |
| 质量优化 | 未提及 | **Prompt 重写 + 3 层退化检测 + section keywords 排除** | notes/16 方案 |
