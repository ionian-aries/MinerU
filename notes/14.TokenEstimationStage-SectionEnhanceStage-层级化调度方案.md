## 1. 设计目标

在 SectionBuildStage 产出的层级化 section tree 基础上，实现：
- 精确的 token 预算计算
- 自适应的 LLM 调用调度（全量单次 / 分组并发 / 超长回退）
- 最大化 LLM 调用效率，最小化 HTTP 请求次数
- 支持层级化增强（叶子节点先增强，父节点基于子结果汇聚）

## 3. Pipeline 编排（8 阶段）

```
Stage 1:  InputStage
Stage 2:  SectionBuildStage
Stage 2b: SectionPlanStage (LLM 驱动的自适应 Section 规划，详见 notes/19)
Stage 3:  TokenEstimationStage
Stage 4:  SectionEnhanceStage
Stage 5:  DocEnhanceStage
Stage 6:  ValidateStage
Stage 7:  ComposeStage
```

**统一基础设施**（定义在 `utils.py`，全流程复用）：
- `TokenCounter`: 精确/粗估双模式 token 计数器（优先 HuggingFace tokenizer，fallback 字符估算）
- `resolve_context_window()`: 五层 fallback 获取上下文长度
- `split_text_by_token_budget()`: 按 token 预算切分文本

**TokenCounter 只创建一次**：pipeline.py 从 provider.token_counter() 获取实例，传给所有 stage，避免重复加载 tokenizer。

## 4. TokenEstimationStage 详细设计

### 4.1 职责边界

**做的事**：
- 获取模型上下文长度（五层 fallback）
- 遍历 section tree，计算每个节点的 token 数
- 计算可用输入 token 预算

**不做的事**：
- 不做 LLM 调用
- 不做装箱决策
- 不做超长切分

### 4.2 上下文长度获取策略（五层 fallback）

```
优先级 1: MINERU_ENHANCE_CONTEXT_WINDOW 环境变量
  → 用户显式写死，最高优先级

优先级 2: HuggingFace AutoTokenizer → model_max_length
  → 加载 tokenizer 时顺便获取
  → provider 初始化时已加载，直接复用

优先级 3: LiteLLM model_prices JSON（本地缓存 + CDN 拉取）
  → 解析 model_prices_and_context_window.json
  → 匹配 MODEL_REFERENCE → max_input_tokens

优先级 4: /models API 探测
  → 向 MINERU_ENHANCE_API_BASE/models 发起 GET
  → vLLM 返回 max_model_len，Ollama 返回 context_length

优先级 5: 兜底值 8192
  → 最保守值，确保不会超限
```

### 4.3 Token 计算

```python
def _walk(node: SectionNode) -> int:
    node.estimated_tokens = token_counter.count(node.own_text)
    subtree = node.estimated_tokens
    for c in node.children:
        subtree += _walk(c)
    node.subtree_tokens = subtree
    return subtree
```

### 4.4 函数签名

```python
def run_token_estimation_stage(
    section_tree: SectionNode,
    model_reference: str,
    safety_ratio: float = 0.85,
    token_counter: TokenCounter | None = None,  # 复用已创建的实例
    base_url: str = "",                          # 用于 /models API 探测
    api_key: str = "",
) -> tuple[SectionNode, int, int]:
    """返回: (带 token 数据的 tree, context_window, available_input_tokens)"""
```

## 5. SectionEnhanceStage 详细设计

### 5.1 核心调度策略（三模式自适应）

| 模式 | 触发条件 | 策略 | 效率 |
|------|---------|------|------|
| **Mode A 全量单次** | 总 token ≤ available_input_tokens × 0.9 | 一次 batch 调用 | 最高 |
| **Mode B 分组并发** | 总量超限，但每个任务不超限 | FFD 装箱 → 多 batch → 并发 | 中等 |
| **Mode C 超长回退** | 单任务超过可用上限 | 切分 → map-reduce 归并 | 最低 |

### 5.2 完整执行流程

#### Phase 1：收集叶子任务
从 tree 按 `enhance_depth` 收集需要增强的叶子节点。叶子的 text = `_gather_subtree_own_text(node)`（递归收集子树全部 own_text）。

#### Phase 2：超长检测与切分（Mode C）
单任务 token > 单请求预算 → `split_text_by_token_budget()` 切分 → 生成 chunk tasks。

#### Phase 3：排序 + FFD 装箱（Mode A/B）
- 所有任务按 estimated_tokens 从大到小排序
- FFD（First-Fit Decreasing）贪心装箱
- Mode A：所有任务装入一个 batch
- Mode B：装不下时开新 batch

#### Phase 4：并发执行
`ThreadPoolExecutor(max_workers=concurrency)` 并发执行多个 batch。

**失败退化机制**：
- batch 调用失败 → 重试 1 次
- 再失败 → 拆为逐个单 section 调用

#### Phase 5：map-reduce 归并
chunk 结果按序收集 → 拼接 summaries + main_ideas → 做一次归并增强调用。

#### Phase 6：父节点增强（bottom-up）
从 `enhance_depth-1` 层到 L1，每层收集有 children 的父节点：
- 父节点输入 = own_text + 子节点 summaries 拼接
- 这些父节点作为新任务，走同样的 Mode A/B/C 流程

#### Phase 7：构建嵌套输出
递归构建 section_results，支持 `subsections` 嵌套字段。

### 5.3 Prompt 模板

| 模板 | 用途 | 输出格式 |
|------|------|---------|
| `section_summary.j2` | 单 section（map-reduce chunk、失败退化） | `{summary, keywords, main_idea}` |
| `section_batch_summary.j2` | Batch 模式（Mode A/B） | `{section_id: {summary, keywords, main_idea}, ...}` |

### 5.4 函数签名

```python
def run_section_enhance_stage(
    *,
    section_tree: SectionNode,
    provider: Any,
    model_reference: str,
    context_window: int,
    available_input_tokens: int,

    language: str = "zh",
    token_counter: TokenCounter | None = None,  # 复用
) -> list[dict[str, Any]]:
    """返回: section_results 列表，支持嵌套 subsections 字段"""
```

## 6. DocEnhanceStage 设计

### 6.1 输入
只使用 L1 section 的增强结果（去掉 subsections 减少 prompt 噪音）。

### 6.2 处理流程
1. 拼接 L1 summaries 作为输入
2. token 数 ≤ 90% 可用 → Mode A 单次调用
3. 超限 → 分组局部汇总 → 全局归并（map-reduce）

### 6.3 容错
- 父节点失败但子节点成功 → 退化为使用成功子树的 summary 合并

### 6.4 函数签名

```python
def run_doc_enhance_stage(
    *,
    provider: Any,
    section_results: list[dict[str, Any]],
    language: str,
    model_reference: str,
    available_input_tokens: int,
    token_counter: TokenCounter | None = None,  # 复用
) -> dict[str, Any]:
    """返回: { global_summary, global_keywords, doc_outline_insights }
    doc_outline_insights 为 { text, section_id }[]；详见 notes/15。
    """
```

**注**：DocEnhanceStage 与 `enhance.json` 的 `overview` **仅**包含 `global_summary` / `global_keywords` / `doc_outline_insights`；模型输出经 `_finalize_doc_payload` 收敛为三键，`doc_outline_insights` 仅接受 `{text, section_id}` 对象数组。

## 7. 输出格式设计

**延伸阅读**：文档级「检索向摘要 + 带 `section_id` 的洞察」契约、离线评测集与门禁阈值，以 **`notes/15.Enhancement契约-检索与引用.md`** 为准；本章 §7.2～§7.4 若与实现不一致时，优先对齐 notes/15 与代码。

### 7.1 两个产物的不同定位

| 产物 | 消费者 | 格式策略 |
|------|--------|---------|
| `enhance.json` | API/后端/下游 pipeline | 结构化 JSON，key 精简，indent=2 |
| `enhanced.md` | 人类预览 + RAG/检索 | 人可读 key:value，block_refs 不出现 |

### 7.2 `enhance.json` 格式（✅ 已实现）

```json
{
  "doc_name": "demo1",
  "process_mode": "pipeline",
  "model_info": {
    "provider": "openai_compatible",
    "model": "gpt-4o-mini-2024-07-18"
  },
  "section_plan": {
    "strategy": "skipped",
    "doc_type": "unknown",
    "fragmentation_rate": 0.1111,
    "original_section_count": 18,
    "enhance_unit_count": 18,
    "fallback": false
  },
  "overview": {
    "global_summary": "全文摘要...",
    "global_keywords": ["关键词1", "关键词2"],
    "doc_outline_insights": [
      { "text": "主题级洞察1", "section_id": "sec_001" },
      { "text": "主题级洞察2", "section_id": "sec_002" }
    ]
  },
  "sections": [
    {
      "id": "sec_001",
      "title": "The response of flow...",
      "page_range": [0, 12],
      "refs": [[0, 0, "title"], [0, 1, "paragraph"], [0, 2, "paragraph"]],
      "status": "success",
      "summary": "章节摘要...",
      "keywords": ["关键词1", "关键词2"],
      "main_idea": "核心观点...",
      "subsections": [...]
    },
    {
      "id": "sec_010",
      "title": "术语与定义",
      "merge_type": "merged",
      "source_section_ids": ["sec_010", "sec_011", "sec_012"],
      "page_range": [2, 3],
      "refs": [[2, 0, "title"], [2, 1, "paragraph"], [3, 0, "title"]],
      "status": "success",
      "summary": "合并单元摘要...",
      "keywords": ["术语1", "术语2"],
      "main_idea": "核心观点..."
    }
  ]
}
```

**Key 转换策略（全链路原生输出，无出口映射）**：

LLM prompt 模板（`.j2`）应尽量直接定义最终标准 key。Doc 级 overview 已直接输出标准 key；section batch 顶层的 `section_id` 仍保留为任务路由键，不作为最终输出字段写入。

| 转换位置 | 源 key | 标准 key | 说明 |
|---------|--------|---------|------|
| `stages_section_enhance._build_result_tree()` | `SectionNode.section_id` | `id` | 构建输出 dict 时写 `"id": node.section_id` |
| `stages_section_enhance._refs_to_tuples()` | `[{page_idx, block_idx, type}]` | `[[page, block, type]]` | 构建输出 dict 时转换 |

**不需要映射的 key**（LLM 输出 = 存储格式）：
- `summary` / `keywords` / `main_idea`（section 级，LLM 直接返回标准 key）
- `page_range`（内部数据结构直接传递）
- `status`（stage 内部直接写入）

**设计原则**：
- doc 级 `schema_hint` 与 prompt 模板直接定义标准 key，避免额外映射
- `SectionNode.section_id`（Python dataclass 属性名）不改 — 那是内部数据结构
- **没有映射层** — 各 stage 原生输出标准 key，pipeline.py 直接组装

**与旧方案的区别**：
- ~~旧方案: 各 stage 使用 `section_id`/`block_refs`/`global_summary` 等内部 key，pipeline.py 出口做统一 `_map_*` 映射~~
- 新方案: doc 级 LLM 从源头直接输出标准 key；内部对象仅在导出 dict 时做必要序列化，无映射层

**`refs` 格式**：`[[0, 0, "title"], [0, 1, "paragraph"]]` — 三元组数组。比对象数组紧凑 3 倍，仍是合法 JSON 可直接解析，比字符串 `"p0b0:t|p0b1:p"` 可读得多。

**`overview`**：外层 JSON 上下文已是 doc 级别；子字段中 `global_*` 与全文摘要/关键词对应；**`doc_outline_insights`** 保留 `doc_` 前缀以区别于历史键 `outline` 及纯字符串列表形态（契约见 notes/15）。

### 7.3 `enhanced.md` 格式（✅ 已实现）

**doc_overview**：
```markdown
<enhance type="overview">
全文摘要: 本研究探讨了植被变化对流量持续曲线的影响...
关键词: 植被变化, 流量持续曲线, 水文循环, 模型建立
洞察提纲:
- [sec_001] 植被变化对流量持续曲线的影响（主题概括）
- [sec_002] 研究目标与方法概述
</enhance>
```

**section**：
```markdown
## 2. Methods
<enhance id="sec_004" pages="2-2">
摘要: 本节描述了研究方法的总体框架。
关键词: 研究方法, 数据收集, 模型拟合
核心观点: 概述研究方法及其步骤。
</enhance>
```

**设计决策**：

| 决策 | 说明 |
|------|------|
| 有 `id` = section，无 `id` = overview | 用 `type="overview"` 区分 |
| `pages` 格式 `"2-2"` 或 `"0-12"` | 紧凑人可读 |
| body 用中文 `key: value` | 不用 JSON，人可读 |
| `keywords` 逗号分隔纯文本 | 不用 JSON 数组 |
| `doc_outline_insights` 洞察每条 `- [sec_xxx] 文本` | 与 JSON 中 `section_id` 一致 |
| `block_refs` 不在 md 中 | 纯机器数据，只在 json 中 |
| 失败的 section 不输出 enhance | 不在 md 中暴露失败状态 |

### 7.4 字段语义统一说明

**overview vs section 字段对照**：

| 语义 | overview 中的 key | section 中的 key | md 中的标签 | 说明 |
|------|------------------|-----------------|------------|------|
| 全文摘要 | `global_summary` | — | `全文摘要:` | 文档级；详见 notes/15 |
| 关键词 | `global_keywords` | `keywords` | `关键词:` | 文档级 vs 章节级 |
| 可引用洞察 | `doc_outline_insights`（`{text, section_id}[]`） | `main_idea` (string) | `洞察提纲:` / `核心观点:` | overview 为多条带引用；section 为单句论点 |

**为什么 overview 的 `doc_outline_insights` ≠ section 的 `main_idea`**：
- overview 的 `doc_outline_insights` 是全文级**命题列表**，且每条绑定 `section_id` 供核验与召回
- `main_idea` 是单章**一句话论点**
- 语义不同；细节以 **notes/15** 为准

### 7.5 预计压缩效果

## 8. 各 Stage 职责边界（最终版）

| Stage | 职责 | 输入 | 输出 |
|-------|------|------|------|
| **1. InputStage** | 校验输入数据 | middle_json, content_list_v2 | context |
| **2. SectionBuildStage** | 结构切分（纯规则，零 LLM，零 token） | content_list_v2 | SectionNode tree |
| **2b. SectionPlanStage** | 碎片化文档自适应分组（notes/19） | SectionNode tree | EnhanceUnit tree + plan_result |
| **3. TokenEstimationStage** | 计算 token 数 + 获取上下文长度 | EnhanceUnit tree | 带 token 的 tree + context_window |
| **4. SectionEnhanceStage** | 层级化增强：装箱→并发→map-reduce→父节点汇聚 | 带 token 的 tree | section_results（嵌套） |
| **5. DocEnhanceStage** | 全文汇总 | section_results L1 | overview |
| **6. ValidateStage** | schema + 内容校验 | section_results + overview | 校验后结果 |
| **7. ComposeStage** | 输出 enhanced.md | 所有结果 + raw_md | 最终 md |
