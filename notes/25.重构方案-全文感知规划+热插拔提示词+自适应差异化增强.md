## 1. 总体架构

```
middle_json['pdf_info'][*]['para_blocks']
    │
    ▼
Stage 1: BlockIndexer
    │  list[TitleItem | BodyItem]（flat 物理顺序）
    │  BodyItem.block_items: list[BlockUnit]
    │  ImageBlockUnit 携带 img_path / caption_text / footnote_text
    ▼
Stage 1.5: ImageEnhanceStage（可选，enabled 开关控制）
    │  多模态 LLM 为每个 image/chart BlockUnit 生成描述
    │  追加到 bu.rendered_text → BodyItem.body_text / char_count 自动更新
    ▼
Stage 2: Hybrid Chunk Planner
    │  list[EnhanceUnit]（含 char_count / estimated_tokens / enhance_guidance）
    ▼
Stage 3: passthrough（仅透传 context_window）
    │  list[EnhanceUnit]（不变）
    ▼
Stage 4: Universal Section Enhance
    │  list[dict]（flat 增强结果）
    ▼
Stage 5: DocEnhanceStage
    ▼
Stage 6: ValidateStage
    ▼
Stage 7: ComposeStage
    │
    ▼
(enhance.json, enhanced.md)
```

## 2. Stage 1：BlockIndexer

**文件**：`mineru/custom/enhance_mvp/process_steps/step_1_build_block_items.py`

### 2.1 数据源

从 `middle_json['pdf_info']`（list）中逐页读取 `para_blocks`。每个 `para_block` 有 `type`、`lines`、`bbox` 等字段。

### 2.2 输出数据结构

```python
@dataclass
class TitleItem:
    title_text: str
    block_ref: list  # [page_no, layout_no, type_str, bbox_str]

@dataclass
class BodyItem:
    char_count: int = 0
    block_refs: list[list] = ...  # 四元组列表
    body_text: str = ""           # make_blocks_to_markdown 渲染结果
    image_count: int = 0
    table_count: int = 0
```

### 2.3 扫描逻辑

- `title`/`doc_title`/`paragraph_title` 类型块 → 创建 `TitleItem`，前一段 `BodyItem` 入栈
- 其他块 → 追加到当前 `BodyItem`
  - 视觉父块（IMAGE/CHART/CODE/TABLE）：展开 `blocks` 子块分别占号，跳过 `cross_page=True` 的子块
  - 普通块：直接占一个 `layout_no`
- `body_text` 调用 `make_blocks_to_markdown(MM_MD)` 渲染，与 raw_md 口径一致

### 2.4 layout_no 编号规则

`layout_no` 为 per-page 递增整数（严格复刻 `draw_layout_bbox` 的 append 顺序）。refs 四元组：`[page_no(1-based), layout_no, type_str, bbox_str]`。

## 3. Stage 2：Hybrid Chunk Planner

**文件**：`mineru/custom/enhance_mvp/process_steps/step_2_section_plan.py`

LLM 的职责是**分块规划**而非内容分类：以文档标题边界为候选段，根据字符数约束决定是否合并，并为每个最终分块提供增强指导意见（`enhance_guidance`）。

### 3.1 算法流程

```
Phase A: 候选段生成（纯规则）
  每个 TitleItem + 紧随的 BodyItem = 1 个候选段
  候选段字符数 = len(body_text)（title 字符数显示在 flat_table chars 列）

Phase B: token 预算计算
  _calc_per_body_budget() 均分可用 token 给各 body 行
  system prompt + title tokens + output reserve 固定消耗先扣除

Phase C: 构建 5 列 flat_table
  type | text（自适应截断） | chars | refs | visual
  体现候选段字符密度，LLM 据此决定是否合并

Phase D: LLM 规划调用
  目标：合并 chars < chunk_min_chars 的候选段；不合并超过 chunk_max_chars 的段
  输出：doc_type + sections（seq_ids / title / enhance_guidance / rationale）
  最多重试 3 次，prompt 逐步强化 seq_ids 覆盖约束

Phase E: 三层校验 + 自动修复
  Layer 1 存在性：过滤越界 seq_id
  Layer 2 连续性：将不连续组拆为多个连续段
  Layer 3 覆盖性：补全未被覆盖的 seq_id（自动填入「章节NN」）

Phase F: build_enhance_units()
  section_id 在此处分配（s001, s002, …）
  inline 填写 char_count = len(body_text)
  inline 填写 estimated_tokens = token_counter.count(body_text)
```

### 3.2 LLM 输入（5 列 flat_table）

```
type      | text（自适应截断）      | chars | refs         | visual
title[00] | "第1章 范围"            | 6     | 1,1,title    | -
body      | "本标准规定了..."       | 420   | 1,2,text     | -
title[01] | "第2章 规范性引用文件"   | 10    | 1,3,title    | -
body      | "..."                  | 85    | 1,4,text     | -
```

### 3.3 LLM 输出 Schema

```json
{
  "doc_type": "对文档类型和用途的简洁描述",
  "sections": [
    {
      "seq_ids": [0, 1],
      "title": "范围与规范性引用文件",
      "enhance_guidance": "提取适用范围边界及引用标准编号，重点标注数值限定条件；用户常以"XX标准适用于哪些产品"查询此节",
      "rationale": "两节信息密度低，合并后chars=505符合chunk_min_chars=200要求"
    }
  ]
}
```

### 3.4 字符数约束配置

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `chunk_min_chars` | 200 | 低于此值的候选段应合并 |
| `chunk_max_chars` | 3000 | 超过此值的段不再合并（Stage 4 Mode C 处理超长） |

配置来自 `enhance_cfg`（`custom_config.enhance`），可在 YAML 中覆盖：

```yaml
enhance:
  chunk_min_chars: 200
  chunk_max_chars: 3000
```

### 3.5 滑动窗口（超长文档）

当 `total_needed > available_input_tokens` 时启用：

- `_partition_windows()`：贪心填充窗口，单窗口超预算则停止
- 相邻窗口重叠 2 个 title，保证边界语义一致
- 重叠 section 取后一窗口结果（有更完整的后续上下文）
- 单窗口失败 → 该窗口内 title 各自独立成节（fallback），不影响其他窗口

### 3.6 Fallback 策略

| 触发条件 | 结果 |
|---------|------|
| 无 title blocks | 整文档作为 1 个 EnhanceUnit |
| LLM 连续 3 次失败 | 每个 TitleItem 独立成节（`enhance_guidance=""`） |
| 滑动窗口合并失败 | 同上 |

`SectionPlanResult.fallback_reason` 记录触发原因（`no_titles` / `llm_failed` / `sliding_window_failed`），写入 `enhance.json` 的 `section_plan` 段，无需看日志即可定位问题。

### 3.7 SectionPlanResult

```python
@dataclass
class SectionPlanResult:
    strategy: str           # "llm_assisted" | "skipped" | "fallback"
    doc_type: str           # LLM 推断的文档类型
    fragmentation_rate: float   # 1 - enhance_units / original_section_count
    original_section_count: int
    enhance_unit_count: int
    llm_calls: int
    fallback: bool
    fallback_reason: str = ""
```

## 5. Stage 4：Universal Section Enhance

**文件**：`mineru/custom/enhance_mvp/process_steps/step_4_section_enhance.py`

### 5.1 路由逻辑（2路）

```python
for unit in enhance_units:
    if not unit.body_text.strip():
        # 路由1：无内容 → 直接跳过
        output.append({..., "status": "skipped_no_content"})
    else:
        # 路由2：有内容 → 统一进批量增强流程
        batch_tasks.append(...)
```

所有有内容的 section 使用同一套模板，通过 `enhance_guidance` 字段实现内容感知的差异化增强。

### 5.2 批量调度（Mode A/B/C）

**Mode A**：全量 sections 能放进单次请求（token 预算充足）→ 一次批量调用

**Mode B**：FFD（First-Fit Decreasing）装箱，按 estimated_tokens 降序排列，贪心填充每个 batch，ThreadPoolExecutor 并发执行

**Mode C**：单个 section 超过 `single_section_budget` → `split_text_by_token_budget()` 拆成多个 chunk，各 chunk 独立增强，最后 map-reduce 归并（拼接各 chunk 的 summary + main_idea 后再调用一次 LLM 综合）

批量失败时自动降级为逐 section 单独调用。

### 5.3 max_tokens 估算

```python
def _estimate_max_tokens(unit: EnhanceUnit) -> int:
    base = 150 + unit.char_count // 4   # 输出约为输入字符的 1/4
    return max(400, min(base, 2000))
```

### 5.4 批量 prompt 中 enhance_guidance 的传递方式

per-section `enhance_guidance` 内嵌在各 section 文本块中，而非 top-level 字段：

```
section_id: s001
title: 范围与适用对象
enhance_guidance: 提取适用范围边界，重点标注数值限定条件；...
text:
<正文内容>

section_id: s002
title: 术语定义
text:
<正文内容>
```

这样不同 section 的 guidance 互不干扰。

### 5.5 输出字段

```json
{
  "id": "s001",
  "title": "范围与适用对象",
  "anchor_title": "第1章 范围",
  "page_range": [1, 2],
  "refs": [[1, 2, "text"], [1, 3, "text"]],
  "pos_range": {"start": [1, 120], "end": [2, 480]},
  "status": "success",
  "summary": "...",
  "keywords": ["...", "..."],
  "main_idea": "...",
  "questions": ["...?", "...?"]
}
```

`pos_range` 由 pipeline.py 后处理阶段从 refs 中的 `bbox_str` 解析写入（`start=[page_no, y0]`，`end=[page_no, y1]`）。

## 6. 核心数据结构

### 6.1 EnhanceUnit

```python
@dataclass
class EnhanceUnit:
    section_id: str          # "s001", "s002", …（Stage 2 三层校验通过后分配）
    title: str               # LLM 给出或继承自原始 TitleItem
    seq_ids: list[int]       # 覆盖的 TitleItem 枚举位置（连续整数列表）
    body_text: str           # 拼接的正文文本
    block_refs: list[list]   # 四元组列表（TitleItem + BodyItem refs 有序 union）
    page_range: list[int]    # [min_page_no, max_page_no]

    anchor_title: str = ""   # 首个原始 TitleItem 文本，ComposeStage 定位 markdown 标题行用
    estimated_tokens: int = 0   # body_text token 数（Stage 2 inline）
    char_count: int = 0         # body_text 字符数（Stage 2 inline）
    enhance_guidance: str = ""  # Stage 2 LLM 写入的增强指导（1-3句话）
    image_count: int = 0
    table_count: int = 0
```

## 7. Prompt 模板

| 模板 | 用途 |
|------|------|
| `section_plan_sys.j2` | Stage 2 system prompt：分块核心原则（字符数约束 > 语义完整性 > 独立成节规则）+ enhance_guidance 写作要求 |
| `section_plan.j2` | Stage 2 user prompt：注入 flat_table + chunk_min_chars/chunk_max_chars 约束，指定输出 JSON 格式 |
| `section_enhance.j2` | Stage 4 单节增强：含 `{% if enhance_guidance %}` 条件块，enhance_guidance 为空时行为与标准增强一致 |
| `section_batch_summary.j2` | Stage 4 批量增强：per-section enhance_guidance 内嵌在 sections_block 中 |
| `section_summary.j2` | 兼容备用（含 enhance_guidance 条件块） |

### section_plan_sys.j2 分块规则优先级

```
1. 字符数约束（最高优先级）
   - < chunk_min_chars → 必须合并至语义最近的相邻段
   - > chunk_max_chars → 不合并（系统自动处理）

2. 语义完整性
   - 多维关联内容（任何单段单独存在会失去语义完整性）
   - 顺序依赖内容（前序结果决定后续步骤）
   - 问答单元不可分

3. 独立成节
   - 语义功能截然不同
   - 高价值独立查询点
   - 已超 chunk_max_chars
```

## 12. Stage 1 改造记录（2026-05-07）

### 12.1 背景与问题

改造前 `BodyItem` 中文本与引用是**两个互相独立的平铺结构**：

```
body_text  = "段落A\n\n表格\n\n段落B\n\n"              ← 一个大字符串
block_refs = [[p1,3,text,...], [p1,4,table,...], ...]   ← 独立列表
```

Stage 2 新方案要求 LLM 给出 `split_at` 块索引来切分长 BodyItem，但旧结构无法将哪段字符对应哪个 ref，子块 refs 无法精确归属。

### 12.2 改造内容

**新增 `BlockUnit` dataclass**（一个 `para_block` = 一个 `BlockUnit`，切割最小原子单元）：

| 字段 | 含义 |
|------|------|
| `rendered_text: str` | `make_blocks_to_markdown` 整体渲染结果（不含末尾 `\n\n`） |
| `block_refs: list[list]` | 四元组 ref 列表。普通块：1 个外层 bbox ref；视觉父块：N 个子块 ref |
| `char_count: int` | `len(rendered_text)`，Stage 2 约束判断用 |
| `image_count: int` | 0 或 1（IMAGE/CHART 为 1） |
| `table_count: int` | 0 或 1（TABLE 为 1） |

**两种块类型的构建差异：**

- **普通块**（text/equation）：`block_refs = [[page_no, layout_no, type, outer_bbox]]`，layout_no 自增 1，外层 `bbox` 作为 ref（覆盖该块所有 lines）
- **视觉父块**（table/image/chart/code）：父块本身不占 layout_no；每个非 cross_page 子块各自 layout_no +1，`block_refs` 为所有子块 ref 的列表；`rendered_text` 是整个父块渲染（一段 markdown）

**`BodyItem` 改为持有 `block_items: list[BlockUnit]`**，原有字段改为 `@property` 聚合推导：

| Property | 推导方式 |
|----------|---------|
| `body_text` | `"".join(bu.rendered_text + "\n\n" for bu in block_items if bu.rendered_text)` |
| `block_refs` | 所有 BlockUnit.block_refs 展开平铺 |
| `char_count` | `sum(bu.char_count)` |
| `image_count` | `sum(bu.image_count)` |
| `table_count` | `sum(bu.table_count)` |

**向后兼容性**：下游 Step 2–7 对上述字段均为只读访问，改为 property 后行为完全一致，无需同步修改。

**其他调整：**
- `_bbox_str` 从 `for page_info` 循环内移到模块级（消除每次迭代重建函数对象）
- BodyItem 非空判断：`block_refs or char_count > 0` → `block_items`
- `__init__.py` 补充导出 `BlockUnit`

### 12.3 Stage 2 使用方式

```
BodyItem.block_items = [BU0(text,200字), BU1(table,0字), BU2(text,150字), BU3(text,300字)]

Stage 2 LLM 给出 split_at=[2]：

子块1 = block_items[0:2]
  body_text  = "段落A\n\n"             ← BU1.rendered_text 为空则跳过
  block_refs = BU0.refs + BU1.refs     ← 表格子块 refs 天然包含
  char_count = 200

子块2 = block_items[2:4]
  body_text  = "段落B\n\n段落C\n\n"
  block_refs = BU2.refs + BU3.refs
  char_count = 450
```

BlockUnit 是不可跨内部切割的原子单元，refs 精确归属，无需字符偏移对齐。

### 12.4 数据流变化

```
改造前：
  para_blocks → BodyItem { body_text: str, block_refs: list, char_count: int }
                           ↑ 文本与引用分离，切分时无法对应

改造后：
  para_blocks → BodyItem { block_items: list[BlockUnit] }
                                         ↑ 文本与引用绑定为原子单元
                           body_text / block_refs / char_count（@property 聚合）
```

## 13. 图片增强方案（Stage 1.5 ImageEnhanceStage）（2026-05-07）

### 13.1 背景与问题

Stage 1 对 image/chart 视觉父块的渲染结果是稀疏占位符：

```
![图1-高温炉装置示意图](images/550e8400...png)
```

Stage 4 LLM 看到的图片信息极少，无法生成准确的 summary / keywords / questions。图片增强的目标：在 Stage 2 分块规划**之前**，用多模态 LLM 为每张图生成语义描述，追加到 BlockUnit.rendered_text，使 Stage 2 和 Stage 4 都能看到富文本内容。

### 13.2 插入位置与原因

```
Stage 1  → build_block_items()
Provider 初始化（pipeline.py）           ← Stage 1.5 依赖 provider
Stage 1.5 → run_image_enhance_stage()   ← 此处插入
Stage 2  → run_section_plan_stage()     ← 依赖正确的 char_count
```

**必须在 Stage 2 之前**：Stage 2 的 token 预算计算基于 `BodyItem.char_count`（@property 自动聚合自 `BlockUnit.char_count`）。增强描述追加到 `bu.rendered_text` 后，`bu.char_count` 和 `item.char_count` 立即更新，Stage 2 拿到的是增强后的正确字符数。

### 13.3 增强决策矩阵

| 块类型 | 条件 | 是否增强 | 原因 |
|---|---|---|---|
| `image_body` / `chart_body` | 有 img_path | **是** | 纯视觉内容，无结构化文字 |
| `table_body` | HTML 非空 | **否** | HTML 已覆盖完整语义，markdown 表格直接可用 |
| `table_body` | HTML 为空/缺失 | **是** | HTML 识别失败，退化为图片 |
| `code_body` | — | **否** | 代码文本已提取，无视觉增值 |

**实现收口**：Stage 1 构建视觉父块 BlockUnit 时，TABLE 类型若 HTML 非空则 `img_path=""` 不存。Stage 1.5 统一用 `if not bu.img_path: continue` 跳过，无需感知块类型。

### 13.4 BlockUnit 扩展（Stage 1 改造点）

在 `BlockUnit` dataclass 新增三个可选字段（仅对 image/chart/table-no-html 类型有值，其余为空字符串）：

| 新增字段 | 来源 | 说明 |
|---|---|---|
| `img_path: str = ""` | `image_body` / `chart_body` / `table_body` span 的 `image_path` 字段 | 图片文件路径（含 hash/UUID），Stage 1.5 的图片输入 |
| `caption_text: str = ""` | `image_caption` / `chart_caption` / `table_caption` 子块 spans content 拼接 | 完整图题文字（存入 BlockUnit，不截断） |
| `footnote_text: str = ""` | `image_footnote` / `chart_footnote` / `table_footnote` 子块 spans content 拼接 | 图注/补充说明/来源标注 |

**`build_block_items` 视觉父块分支改造：**

```
遍历 parent.blocks 子块：
  *_body    → 取 img_path（图片文件路径）
  *_caption → 拼接 caption_text（所有 spans content）
  *_footnote → 拼接 footnote_text（所有 spans content）

TABLE 特殊判断：
  table_body span["html"] 非空 → img_path = ""（不存，跳过增强）
  table_body span["html"] 为空 → img_path = span["image_path"]（存入，触发增强）

构建 BlockUnit(rendered_text, block_refs, char_count, image_count, table_count,
               img_path=img_path, caption_text=caption_text, footnote_text=footnote_text)
```

`rendered_text` 仍由 `make_blocks_to_markdown` 整块渲染，不变。新增字段仅供 Stage 1.5 使用，对 Stage 2–7 透明。

### 13.5 Stage 1.5 完整处理流程

**Phase 0：启动检查（文档级，执行一次）**

```
image_enhance_cfg.enabled = False  → 整个 Stage 1.5 跳过，直接进 Stage 2
provider 不支持 vision 接口        → 同上，跳过（无 text-only 降级）
```

不存在 text-only 模式：视觉增强的核心价值在于让 LLM 看到图片内容；caption/footnote 已存在于 rendered_text 中，无多模态能力时无需重复生成。

**Phase 1：滚动扫描 items，维护 current_title（正向一次）**

```
current_title = ""
for i, item in enumerate(items):
    if TitleItem → current_title = item.title_text
    if BodyItem  → section_title_index[i] = current_title
```

唯一的预扫描步骤，无需 prev_body / next_body 索引。

**Phase 2：逐 BodyItem → 逐 BlockUnit，收集待增强任务**

```
all_tasks = []   # (item_index, bu_index, ImageContext)

for i, item in enumerate(items):
    if not isinstance(item, BodyItem): continue
    if item.image_count == 0: continue          # 快速跳过无图 BodyItem

    section_title = section_title_index[i]

    for j, bu in enumerate(item.block_items):
        if bu.image_count != 1: continue        # 非图片块跳过
        if not bu.img_path: continue            # img_path 为空跳过（table with HTML 等）

        # min_short_side_px 防御性检查（从 bu.block_refs 的 bbox 字段计算）
        short_side = min_dimension_from_block_refs(bu.block_refs)
        if short_side < config.min_short_side_px: continue

        # 从相邻 BlockUnit 收集上下文（BlockUnit 边界天然清晰）
        text_before = tail_chars(
            [b.rendered_text for b in item.block_items[:j] if b.rendered_text],
            max_chars=250
        )
        text_after = head_chars(
            [b.rendered_text for b in item.block_items[j+1:] if b.rendered_text],
            max_chars=250
        )
        # text_before/after 中其他图片的 ![...](path) 自然保留
        # 连续图片场景：LLM 感知"这里有多张图"，但每次只处理当前图

        context = ImageContext(
            item_index    = i,
            bu_index      = j,
            img_path      = bu.img_path,
            caption_text  = bu.caption_text,
            footnote_text = bu.footnote_text,
            section_title = section_title,
            text_before   = text_before,
            text_after    = text_after,
        )
        all_tasks.append((i, j, context))
```

**Phase 3：并发多模态 LLM 调用**

```
ThreadPoolExecutor(workers = config.concurrency)

对每个 (i, j, context)：
    attempt 1：
        generate_with_image(
            prompt        = build_image_enhance_prompt(context),
            image_path    = context.img_path,
            system_prompt = IMAGE_ENHANCE_SYSTEM_PROMPT,
            max_tokens    = config.max_tokens,
        )
        质量检查：len(result) ≥ 20 字且非空 → 通过
    失败 → attempt 2（处理瞬时 API 错误）
    失败 → results[(i, j)] = None    # no-op，不修改 BlockUnit

results: dict[(i, j)] → enhanced_text or None
```

2 次尝试与 Stage 4 batch fallback 对齐。

**Phase 4：回写 BlockUnit**

```
for (i, j), enhanced_text in results.items():
    if enhanced_text is None: continue           # 增强失败，no-op

    bu = items[i].block_items[j]
    bu.rendered_text += "\n" + enhanced_text    # 追加描述，保留原 ![...](path) 引用
    bu.char_count = len(bu.rendered_text)        # 显式更新

    # BodyItem.char_count = sum(bu.char_count)   → @property 自动更新
    # BodyItem.body_text  = join(bu.rendered_text) → @property 自动更新
    # Stage 2 token budget 基于 item.char_count  → 拿到正确值
```

失败是真正的 no-op：`bu.rendered_text` 不变，body_text 保持原 `![caption](path)` 格式，Stage 2 照常接收。

### 13.6 上下文构建设计（ImageContext）

上下文信息分两层，均来自 items 列表这一单一数据源：

| 层 | 字段 | 来源 | 说明 |
|---|---|---|---|
| BlockUnit 层 | `img_path` | `bu.img_path` | 图片文件，送给多模态 LLM |
| BlockUnit 层 | `caption_text` | `bu.caption_text` | 完整图题（Stage 1 已提取） |
| BlockUnit 层 | `footnote_text` | `bu.footnote_text` | 图注/补充说明 |
| items 层 | `section_title` | 正向滚动扫描 | 最近前置章节标题，提供领域背景 |
| items 层 | `text_before` | `block_items[:j]` 尾部 ≤250 字 | 图前上下文，含其他图片占位符 |
| items 层 | `text_after` | `block_items[j+1:]` 头部 ≤250 字 | 图后上下文，含其他图片占位符 |

**不需要跨 BodyItem 补充**：caption + footnote + section_title + 局部文本已足够；相邻 BodyItem 可能属于不同主题，引入反而产生噪声。

**不需要后置 section_title**：当前图的语义由前置标题和 caption 决定，下一节内容与当前图无关。

**连续图片处理**：text_before/after 中其他图片的 `![caption](path)` 自然保留，LLM 感知"这里有多张图"，但每次调用独立聚焦当前图，互不干扰，并行执行。

### 13.7 LLM Prompt 设计

**System Prompt 核心要求：**

```
你是技术文档图片分析助手。
1. 先判断图片类型（数据图表/流程图/架构图/表格截图/实物照片/公式/其他）
2. 依据类型选择描述侧重：
   - 数据图表：趋势、轴标签、关键数值
   - 流程图/架构图：组件、层次关系、流向
   - 表格截图：表头含义、关键数据点
   - 实物照片：对象特征、状态、标注
   - 公式：完整转录公式内容
3. 描述须自包含（不依赖"如图所示""本图"等指代）
4. 保留所有数值、单位、编号
```

**User Prompt 上下文注入顺序：**

```
章节标题：{section_title}
图题：{caption_text}
图注：{footnote_text}（若有）
前文：{text_before}（若有）
后文：{text_after}（若有）
```

**质量校验**：输出长度 ≥ 20 字且非空。不设上限（LLM 输出受 max_tokens 控制）。

### 13.9 配置参数

在 `enhance` 配置块下新增子节：

```yaml
enhance:
  # 现有参数不变
  chunk_min_chars: 200
  chunk_max_chars: 3000
  language: zh
  model: gpt-4o
  concurrency: 4
  safety_ratio: 0.85

  # 新增：图片增强子配置
  image_enhance:
    enabled: false          # 总开关，默认关（功能稳定前不影响主流程）
    model: ""               # 多模态模型 ID，空则继承上层 model（需支持 vision）
    concurrency: 2          # 并发 LLM 调用数（图片 IO bound，默认保守）
    max_tokens: 300         # 每张图 LLM 输出 token 上限
    min_short_side_px: 10   # 防御性像素下限，任意边 < 10px 的块跳过
```

| 参数 | 必要原因 |
|---|---|
| `enabled` | 功能稳定前隔离，不影响现有主流程 |
| `model` | 多模态 LLM 可能与文本 LLM 不同（如 gpt-4o vs gpt-4o-mini） |
| `concurrency` | 图片 API 速率敏感，独立于 Stage 4 的 concurrency 控制 |
| `max_tokens` | 描述长度直接影响 body_text 膨胀量与 API 成本 |
| `min_short_side_px` | 防御性保护，防止极小异常块进入 LLM（值极低，几乎不拦截正常图片） |

### 13.11 边界情况处理

| 情况 | 处理 |
|---|---|
| `enabled=False` | Phase 0 直接跳过，items 不变 |
| provider 不支持 vision | Phase 0 直接跳过 |
| `img_path` 为空（table with HTML） | Phase 2 `if not bu.img_path: continue` |
| bbox 任意边 < `min_short_side_px` | Phase 2 跳过该 BlockUnit |
| 2 次 LLM 尝试均失败 | Phase 4 result=None，bu.rendered_text 不变 |
| 文档无任何图片 | `item.image_count == 0` 全部 continue，Phase 3 无任务 |
| 连续多张图上下文雷同 | 各图独立调用，并行执行；LLM 通过各自 caption 区分 |
| 图片文件不存在于磁盘 | LLM 调用异常 → attempt 2 → 失败 → no-op |
