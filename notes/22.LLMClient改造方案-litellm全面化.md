## 1. 核心设计原则：最优分工

改造后的架构严格分为三层，各层职责互不越界：

```
┌─────────────────────────────────────────────────────────────┐
│  调用方（Stage）                                              │
│  职责：                                                       │
│    - 构建 prompt 和 schema（业务知识）                         │
│    - 预估 token，决定是否需要分段（调用 client.count_tokens）  │
│    - 知道自己的输出结构，提供 merge 策略                       │
│    - schema 校验失败时重试（内容层重试，业务职责）              │
│  看到的：client.generate_json(prompt, ...) → dict             │
│  内部：Stage 自己决策是否调用多次 generate_json，自己 merge    │
├─────────────────────────────────────────────────────────────┤
│  LLMClient（litellm 封装层）                                  │
│  职责：                                                       │
│    - 保证"一次 HTTP 调用"的可靠性（retry/fallback/timeout）   │
│    - 保证返回的是合法 dict（JSON 代码块清洗 + 格式重试）        │
│    - 提供 context_window、count_tokens 供调用方决策            │
│  不做：跨调用的 map-reduce 编排（merge 逻辑是业务敏感的）      │
├─────────────────────────────────────────────────────────────┤
│  litellm                                                      │
│  职责：                                                       │
│    - HTTP 层 retry（429/5xx 指数退避）                        │
│    - 模型 fallback（主模型失败自动切换备用模型）               │
│    - timeout、drop_params、response_format                    │
└─────────────────────────────────────────────────────────────┘
```

**为什么 map-reduce 不放进 LLMClient**：merge 步骤依赖输出结构，不同调用的 merge 方式完全不同（SectionEnhance 的 merge 是拼接摘要；DocEnhance 的 merge 是层级汇总；SectionPlan 的 merge 需要重新编号 seq_ids）。通用化会导致 API 复杂或质量损失，将 merge 保留在 Stage 职责范围内是正确的分工。

## 2. 三层重试架构（改造后）

```
调用方 Stage（业务层重试）
  │ 发现 schema 校验失败 → Stage 自己决定是否重新调用
  ↓
client.generate_json(prompt, system_prompt, schema_hint, max_tokens)
  │
  ├─ [格式层] _do_completion() 返回 content
  │     ↓ _extract_json(content) 失败？
  │       是 → 强化 system_prompt，再调一次 _do_completion
  │       二次失败 → 抛 JSONParseError，Stage try/except 处理
  │
  └─→ _do_completion(messages, max_tokens)
        │
        └── litellm.completion(
              num_retries=2,       ← 429/5xx 自动指数退避（litellm 原生）
              fallbacks=[...],     ← 主模型失败自动切换（litellm 原生）
              timeout=300,
              response_format={"type": "json_object"},
              drop_params=True,    ← 不支持 response_format 的模型静默忽略
            )
            全部失败 → 抛 LLMCallError
```

职责清晰：
- **litellm 管 HTTP 可靠性**（retry/fallback 对调用方透明）
- **LLMClient 管 JSON 格式**（代码块清洗 + 格式重试对调用方透明）
- **Stage 管业务内容**（schema 校验、质量检测、map-reduce 编排）

## 3. LLMClient 接口设计

### 3.1 构造参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `model` | str | 主模型名（litellm 格式，如 `"deepseek/deepseek-chat"`） |
| `base_url` | str | API endpoint |
| `api_key` | str | API key |
| `fallback_models` | list[FallbackModel] | 备用模型列表（有序，主模型失败时按序切换） |
| `timeout_s` | int | 每次 HTTP 调用超时（秒），默认 300 |
| `http_retries` | int | litellm `num_retries`，默认 2 |
| `max_output_tokens` | int \| None | 全局输出 token 上限（调用方传值优先，均未设则模型自决） |
| `context_window_override` | int \| None | 显式覆盖自动检测的上下文窗口大小 |
| `hf_tokenizer` | str \| None | HuggingFace tokenizer ID（覆盖 litellm 不认识的私有模型） |
| `safety_ratio` | float | 上下文安全系数，默认 0.85 |

`FallbackModel` 结构：`{name, api_base, api_key}`，其中 `api_base` 和 `api_key` 可选（不填则复用主模型 endpoint，适合同一服务部署多模型场景）。

### 3.2 核心方法

```
generate_json(
    prompt: str,               # 用户提示词（内容部分）
    system_prompt: str,        # 系统提示词（指令部分）
    schema_hint: str = "",     # JSON schema 约束，追加到 prompt 末尾
    max_tokens: int | None,    # 本次调用输出 token 上限
                               #   调用方传值 > 全局 max_output_tokens > 不传（模型自决）
) -> dict
```

**保证**：返回合法 dict，或抛出 `LLMCallError` / `JSONParseError`。
**不保证**：dict 的内容符合业务 schema（这是 Stage 的职责）。

```
count_tokens(text: str) -> int
count_messages(messages: list[dict]) -> int
```

供调用方在分段决策时使用。

```
context_window: int   # 属性，构造时一次性解析并缓存
```

### 3.3 异常类型

| 异常 | 触发时机 | Stage 处理建议 |
|------|---------|--------------|
| `LLMCallError` | litellm 所有 retry 和 fallback 耗尽后仍失败 | try/except，触发 Stage 级兜底（如返回 failed 状态） |
| `JSONParseError` | 两次 JSON 解析尝试均失败 | 同上 |

**不需要失败回调**：当前三个 Stage 的失败处理逻辑各不相同（SectionPlan fallback 到 standalone；SectionEnhance 标记 `status: failed`；DocEnhance 返回 `_fallback_doc_payload()`），都是业务决策，放在 Stage 的 try/except 中即可。回调会把 Stage 业务逻辑和 client 耦合，增加复杂度且无收益。

## 4. 各能力实现细节

### 4.1 JSON 代码块清洗（_extract_json）

模型返回格式可能是以下任意一种：
- 纯 JSON：`{"key": "value"}`
- 代码块包装：` ```json\n{"key": "value"}\n``` `
- 有说明文字：`以下是结果：\n{"key": "value"}`

处理链：
1. 正则匹配 ` ```json...``` ` 或 ` ```...``` ` → 提取花括号内容
2. 找最外层 `{...}` 块（处理前后有说明文字的情况）
3. 直接 `json.loads`（干净输出走这条路）

### 4.2 JSON 格式重试

第一次 `_extract_json` 失败后：
- 在 system_prompt 末尾追加"只允许输出合法 JSON 对象，禁止代码块标记和额外文字"
- 重新调用 `_do_completion`（一次新的 HTTP 调用，包含 litellm 的 num_retries）
- 二次失败抛 `JSONParseError`

### 4.3 Token 计数（分层 fallback）

```
优先级：
1. litellm.token_counter(model=model_name, text=text)
   → litellm 内置 100+ 模型的 tokenizer，覆盖所有主流模型

2. HuggingFace AutoTokenizer（hf_tokenizer 配置项指定）
   → 覆盖 litellm 不认识的私有/微调模型

3. 字符估算兜底
   → 中文：1字 ≈ 1.5 token；ASCII：4字符 ≈ 1 token
```

构造时确定走哪条路，后续 `count_tokens()` 调用直接复用。

### 4.4 上下文窗口检测（分层 fallback）

```
优先级：
1. context_window_override（配置文件显式设置，最高优先级）

2. litellm.get_max_tokens(model_name)
   → litellm 维护完整的模型 context window 数据库

3. HuggingFace tokenizer.model_max_length
   → 覆盖 litellm 数据库没有的模型

4. /models API 运行时探测
   → vLLM / Ollama 部署时能拿到实际加载的 context length

5. 保守兜底 8192
```

**构造时解析一次，缓存为 `self.context_window`**，替代当前 pipeline 中的重复解析（pipeline.py L78 + process_steps/step_3_token_estimation.py L45）。

### 4.5 模型 Fallback

litellm `fallbacks` 参数：
```python
kwargs["fallbacks"] = [
    {"model": m.name, "api_base": m.api_base, "api_key": m.api_key}
    for m in self._fallback_models
]
```

主模型失败后，litellm 自动按序切换备用模型，切换过程对调用方完全透明。备用模型可配置独立的 api_base 和 api_key，支持跨提供商 fallback。

## 5. 各 Stage 改造要点

### 5.1 SectionPlanStage

改动点：在现有 `generate_json()` 调用处传入 `max_tokens=output_reserve`（变量已有，只缺传参）。

超限 fallback 策略维持不变（每 title 独立成节）。窗口分段规划为 P2 优化，本次不实现。

### 5.2 SectionEnhanceStage

改动点：
- `_enhance_single_via_prompt()` 传入 `max_tokens=600`
- `_execute_batch()` 传入 `max_tokens=max(600, len(tasks) * 200)`

Mode A/B/C 的调度逻辑、ThreadPoolExecutor 并发、map-reduce 分块逻辑**全部保留不变**，本次改造只改 provider 层，不动 Stage 编排逻辑。

### 5.3 DocEnhanceStage

改动点：`_generate_doc_payload()` 内所有 5 处 `generate_json()` 调用追加 `max_tokens=1500`。

Mode A/B 的分组 map-reduce 逻辑**保留不变**，DocEnhance 的质量提升（如 reduce 阶段携带 representative sections）为 P2 优化。

## 6. 配置文件新增字段

在现有 `enhance` 配置段追加以下可选字段：

```yaml
enhance:
  # 现有字段保持不变
  model: "deepseek-v3"
  api_base: "https://api.deepseek.com/v1"
  api_key: "sk-xxx"

  # 新增：备用模型列表（可选；主模型失败时 litellm 按序切换）
  fallback_models:
    - name: "qwen2.5-72b"
      api_base: "https://your-qwen-endpoint/v1"
      api_key: "sk-yyy"
    - name: "gpt-4o-mini"
      # api_base / api_key 不填则复用主模型 endpoint

  # 新增：全局输出 token 上限（可选；调用方传值优先；均未设则模型自决）
  max_output_tokens: 2000
```

`custom_config_loader.py` 对应增加校验：
- `fallback_models`：可选，字符串或对象列表，每个元素必须有 `name` 字段
- `max_output_tokens`：可选，正整数
