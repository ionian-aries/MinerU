# MinerU 后端模型与服务依赖说明

如果你在本机（M1 64G）综合考虑速度+效果，我建议：

首选：hybrid-auto-engine（最均衡，默认推荐）
次选：vlm-auto-engine（通常更快一点，效果也高，但在复杂版面上一般不如 hybrid 稳）
可以这样理解：

pipeline：最快/最省资源，但效果明显低一档
vlm-auto-engine：速度与精度都不错
hybrid-auto-engine：精度最好，速度比 vlm-auto-engine 慢一些，但通常更值得


本文整理 `-b/--backend` 中以下 4 个后端的实际依赖：

- `vlm-auto-engine`
- `vlm-http-client`
- `hybrid-auto-engine`
- `hybrid-http-client`

目标：明确每种模式分别需要哪些本地模型、哪些远程服务，以及常用配置项。


# MinerU 三种解析后端差异说明

本文记录 `pipeline`、`vlm`、`hybrid` 三种解析后端的核心区别，便于选型与交接。

## 后端定义

- `pipeline`：`mineru/backend/pipeline/pipeline_analyze.py`
- `vlm`：`mineru/backend/vlm/vlm_analyze.py`
- `hybrid`：`mineru/backend/hybrid/hybrid_analyze.py`

## 核心差异

### 1) `pipeline`

- **架构方式**：传统多模型流水线（版面/OCR/表格/公式等组件化）
- **优势**：兼容性最好，可纯 CPU 运行，部署门槛低
- **劣势**：在复杂版面理解场景中，效果通常弱于 VLM 路线

### 2) `vlm`

- **架构方式**：视觉语言模型主导解析（可接 vLLM/LMDeploy/MLX/Transformers）
- **优势**：复杂文档理解能力更强，通常精度更高
- **劣势**：对硬件和推理环境要求更高，资源消耗更大

### 3) `hybrid`

- **架构方式**：VLM + 小模型混合（全局理解 + OCR/公式等专项增强）
- **优势**：精度与稳定性更均衡，适合复杂、多语言场景
- **劣势**：链路更复杂，调参与运维成本更高

## 选型建议

- **机器一般、追求稳定上线**：优先 `pipeline`
- **GPU 充足、追求解析效果**：优先 `vlm`
- **复杂业务、兼顾效果与鲁棒性**：优先 `hybrid`

## 1. 四种后端总览

| 后端 | 是否需要本地 VLM 模型 | 是否需要本地小模型(pipeline链路) | 是否需要远程 OpenAI 兼容服务 |
| --- | --- | --- | --- |
| `vlm-auto-engine` | 是 | 否 | 否 |
| `vlm-http-client` | 否(客户端侧) | 否 | 是 |
| `hybrid-auto-engine` | 是 | 是 | 否 |
| `hybrid-http-client` | 否(客户端侧) | 是 | 是 |

## 2. 各后端依赖细节

### 2.1 `vlm-auto-engine`

- 本地推理模式，使用本机算力。
- 需要本地 VLM 主模型仓：
  - HuggingFace: `opendatalab/MinerU2.5-2509-1.2B`
  - ModelScope: `OpenDataLab/MinerU2.5-2509-1.2B`
- 不需要 `--url`。
- 引擎由 `auto-engine` 自动选择（不同平台可能选择 `vllm`/`lmdeploy`/`mlx`/`transformers`）。

### 2.2 `vlm-http-client`

- 客户端模式，本地不做 VLM 权重推理。
- 必须提供远程 OpenAI 兼容服务地址：`-u/--url`。
- 远程服务需部署可用于 MinerU 的 VLM 模型（通常是 MinerU 的 VLM 模型服务）。
- 常见可选环境变量：
  - `MINERU_VL_MODEL_NAME`：当远端服务有多个模型时指定模型名。
  - `MINERU_VL_API_KEY`：远端服务鉴权用 API Key。

### 2.3 `hybrid-auto-engine`

- 本地混合推理模式。
- 同时依赖：
  - 本地 VLM 主模型（同 `vlm-auto-engine`）。
  - 本地小模型链路（来源于 `PDF-Extract-Kit-1.0`），常见包含：
    - `models/Layout/PP-DocLayoutV2`
    - `models/OCR/paddleocr_torch`
    - 公式模型（默认 `unimernet_small`，可切 `pp_formulanet_plus_m`）
    - 表格/方向分类等 pipeline 组件（按功能启用）
- 不需要 `--url`。

### 2.4 `hybrid-http-client`

- 远程 + 本地混合模式。
- 必须提供远程 OpenAI 兼容服务地址：`-u/--url`（远程负责 VLM 推理）。
- 本地仍需要小模型链路（OCR/布局/公式等）参与混合后处理。
- 可选：
  - `MINERU_HYBRID_BATCH_RATIO`：常用于控制 hybrid 中小模型链路的显存占用。
  - `MINERU_VL_MODEL_NAME` / `MINERU_VL_API_KEY`：远端模型选择与鉴权。

## 3. 一次性准备模型的建议

若希望避免运行期缺模型，建议直接下载两套模型：

```bash
mineru-models-download -m all
```

含义：

- `vlm` 模型：用于 `vlm-auto-engine` 与 `hybrid-auto-engine` 的本地 VLM 推理。
- `pipeline` 模型：用于 `pipeline` 与 `hybrid-*` 的小模型链路（其中 `hybrid-http-client` 也会用到）。

## 4. 常见命令示例

### 4.1 本地 VLM（不走远程服务）

```bash
mineru -p <input_path> -o <output_path> -b vlm-auto-engine
```

### 4.2 远程 VLM 服务（HTTP Client）

```bash
mineru -p <input_path> -o <output_path> -b vlm-http-client -u http://127.0.0.1:30000
```

### 4.3 本地混合

```bash
mineru -p <input_path> -o <output_path> -b hybrid-auto-engine
```

### 4.4 远程 VLM + 本地小模型混合

```bash
mineru -p <input_path> -o <output_path> -b hybrid-http-client -u http://127.0.0.1:30000
```

---

## 5. 选型建议（简版）

- 机器算力足、想少折腾服务：`hybrid-auto-engine`。
- 本机显存紧张、已有远程模型服务：`hybrid-http-client`。
- 只想走纯 VLM 并尽量减少本地依赖：`vlm-http-client`。
- 完全离线/本地部署：`vlm-auto-engine` 或 `hybrid-auto-engine`。
