# 二开配置解耦：单一配置文件入口方案（最终版）

> **文档定位**：二开配置体系的“唯一真相源”（Single Source of Truth）。本方案用于将二开（enhance/storage/discard）配置从 `~/mineru.json` 与环境变量中彻底解耦，并以“入参指定的单一配置文件”作为唯一配置入口，确保原生 MinerU 功能保持不变、二开默认不介入。  
> **创建日期**：2026-04-21  
> **状态**：📌 方案冻结（待实现）  
> **适用范围**：`mineru` / `razel-mineru` CLI；`mineru-api` FastAPI；（可选）`mineru-router`  

---

## 1. 背景与问题

当前二开配置存在以下风险与不确定性来源：

- 二开通过 `razel-mineru init` 将 `enhance/storage/discard` 段**混入** `~/mineru.json`，使原生配置文件被污染，且容易在多环境/多项目间产生不可控差异。
- 二开大量依赖环境变量（`MINERU_ENHANCE_*`、`MINERU_STORAGE_*`、`MINERU_DISCARD_TYPES` 等），导致**运行时不可复现**、难以审计与回放。
- 代码中存在多处“配置回退链”（CLI / FastAPI / custom 模块内部），可能出现同一任务链路中不同阶段读取到的配置不一致。

本方案的目标是从源头重构配置入口，使二开配置：

- **不再影响 `~/mineru.json`**（不读、不写、不合并、不注入 env）。
- **不再受环境变量影响**（二开完全忽略 env 配置）。
- **仅由一个入参指定的配置文件决定**（单一入口、单次加载、全链路一致）。

---

## 2. 目标与非目标

### 2.1 目标（必须满足）

1. **移除 `razel-mineru init` 命令**：不再提供任何会在 `~/mineru.json` 中追加/合并二开段的行为。
2. **二开配置完全独立**：二开不读 `~/mineru.json`，也不引入 `~/razel-mineru.json` 等替代文件。
3. **二开不使用环境变量**：二开侧忽略所有 `MINERU_ENHANCE_*` / `MINERU_STORAGE_*` / `MINERU_DISCARD_TYPES` / `MINERU_STORAGE_OPTIONS_JSON/FILE` 等。
4. **单一配置文件入口**：
   - CLI：`mineru/razel-mineru parse` 新增 `--custom-config <path>`；不传则二开默认关闭（原生行为零影响）。
   - FastAPI：`mineru-api` 启动时新增 `--custom-config <path>`；不传则二开默认关闭（服务仅提供原生行为）。
5. **单次加载 + 显式传递**：配置文件在入口处读取一次，解析为 `CustomConfig` 对象后，沿调用链显式传递；二开模块内部禁止再次读文件/读 env。

### 2.2 非目标（本方案明确不做）

- 不引入请求级的 `custom_config_path`（避免任意路径读取、安全与一致性风险）。后续如需多租户能力，另开新方案。
- 不更改 MinerU 原生配置体系：`~/mineru.json` 仍由原生模块使用（如 models-dir 等），但二开不再触碰它。
- 不引入 mock / heuristic 回退（保持二开能力的真实行为定义）。

---

## 3. 配置文件格式选择（最终决策）

### 3.1 结论

- **主格式：YAML（`.yaml/.yml`）**
- **兼容：JSON（作为 YAML 子集兼容）**

### 3.2 原则约束

- 二开配置文件**不支持** `${ENV_VAR}` 引用替换（彻底切断 env 影响）。
- 二开配置文件为唯一真相源（Single Source of Truth），禁止“多级回退链”导致的隐式覆盖。

---

## 4. 二开配置 Schema（单一文件入口）

顶层分三段，对齐现有二开模块（`enhance_mvp` / `storage` / `discard_policy`）：

```yaml
enhance:
  enable: false
  provider: openai_compatible
  model: ""               # enable=true 时必填
  api_base: ""            # enable=true 时必填
  api_key: ""             # enable=true 时必填
  model_reference: ""     # 可选；默认等于 model
  language: zh
  depth: 2
  concurrency: 4
  timeout_s: 300
  http_retries: 2
  safety_ratio: 0.85
  context_window: null
  hf_tokenizer: null

  # ── SectionPlanStage 配置 ──
  # 控制碎片化文档（国标/法规/手册等）的自适应分组。
  # 简写形式：section_plan: "auto"  (等价于 section_plan: { enabled: auto })
  section_plan:
    enabled: auto          # auto | off | always
                           #   auto: 碎片率 > threshold 时触发 LLM 分组
                           #   off: 禁用（不做任何分组）
                           #   always: 强制 LLM 分组（不管碎片率）
    threshold: 0.20        # 碎片率阈值（auto 模式下）
    min_chars: 100         # 碎片判定阈值：subtree_chars < min_chars 视为碎片
    max_chars: 5000        # 单个增强单元合并上限（字符数）

storage:
  image:
    backend: local         # local | s3
    # s3_* 字段仅在 backend=s3 时必填
    s3_bucket: ""
    s3_prefix: ""
    s3_ak: ""
    s3_sk: ""
    s3_endpoint_url: ""
    s3_addressing_style: auto
    ref_prefix: ""         # 可选；用于 md 图片引用前缀
  doc:
    backend: local         # local | s3
    s3_bucket: ""
    s3_prefix: ""
    s3_ak: ""
    s3_sk: ""
    s3_endpoint_url: ""
    s3_addressing_style: auto

discard:
  types:
    - header
    - footer
    - page_number
    - aside_text
    - page_footnote
```

### 4.1 校验规则（强约束，Fail-fast）

- `enhance.enable=true` 时，必须提供：
  - `enhance.model`
  - `enhance.api_base`
  - `enhance.api_key`
- `enhance.section_plan` 校验：
  - 字符串形式：值必须为 `auto`、`off`、`always` 之一
  - 对象形式：
    - `enabled`：必须为 `auto`、`off`、`always`（默认 `auto`）
    - `threshold`：必须为 0.0~1.0 的浮点数（默认 0.20）
    - `min_chars`：必须为正整数（默认 100）
    - `max_chars`：必须为正整数（默认 5000）
  - 不传（null/缺失）：使用全部默认值，等同于 `{ enabled: auto, threshold: 0.20, min_chars: 100, max_chars: 5000 }`
- `storage.*.backend=s3` 时，必须提供：
  - `s3_bucket`, `s3_ak`, `s3_sk`, `s3_endpoint_url`
  - `s3_prefix` 可为空但建议给出（便于隔离任务目录）
- `discard.types` 必须为合法 `BlockType` 值集合；包含非法值应直接报错（防止无效配置静默生效）。

---

## 5. 配置加载与优先级（最终规则）

本方案的核心是“唯一配置源”，因此优先级规则非常简单：

### 5.1 二开配置优先级

1. **入参指定的二开配置文件**（唯一来源）
2. （可选）二开模块的代码默认值（仅用于缺失字段的安全默认；不得引入 env/`~/mineru.json` 回退）

### 5.2 明确禁止的回退来源

- 禁止读取 `~/mineru.json` 的 `enhance/storage/discard` 段
- 禁止读取任何 `MINERU_ENHANCE_*` / `MINERU_STORAGE_*` / `MINERU_DISCARD_TYPES`
- 禁止读取 `MINERU_STORAGE_OPTIONS_JSON/FILE`

## 6. 接入方式（CLI / FastAPI / Router）

### 6.1 CLI：`mineru` / `razel-mineru`

#### 6.1.1 新增参数（最终行为）

- `parse` 命令新增：`--custom-config <path>`
- 若 **不传** `--custom-config`：
  - 二开能力默认关闭（enhance/storage/discard 均不介入）
  - CLI 行为保持原生 MinerU 逻辑（对原生零影响）

#### 6.1.2 二开关闭时的行为边界

- `enhance_mvp` 不执行，不生成 `_enhance.json`，md 输出保持原生。
- storage 不覆盖写入策略（仍走原生写入方式/默认 local）。
- discard 不额外注入丢弃策略（仍走原生默认行为）。

> 备注：二开关闭的边界必须在**入口处**判定，避免在深层模块里做隐式判断导致不一致。

---

### 6.2 FastAPI：`mineru-api`

#### 6.2.1 服务级固定配置（最终采用）

- `mineru-api` 启动参数新增：`--custom-config <path>`
- 若启动时 **不传** `--custom-config`：
  - 二开能力默认关闭
  - 服务仅提供原生 MinerU 行为（对原生零影响）

#### 6.2.2 明确不做：请求级 config 引用

本方案不支持在请求体传 `custom_config_path` 或 config id：

- 安全：可能导致任意路径读取
- 性能：频繁加载文件
- 一致性：并发请求可能读取不同版本配置

---

### 6.3 `mineru-router` 是否需要 `--custom-config`？

统一规则（避免歧义）：

- **如果 `mineru-router` 仅做请求转发**到后端 `mineru-api`：router **不需要** `--custom-config`。
- **如果 `mineru-router` 会实际执行解析/写输出/调用增强**（即它本身是执行进程或会启动/管理执行进程）：router **必须**将 `--custom-config` 透传给实际执行的进程，或在自身加载后显式注入执行链路。

换句话说：

> **只要某个进程会“实际执行解析链路”，它就必须持有 custom config；纯代理层不需要。**

## 7. 实现落地点（源头改造清单，供后续开发严格对照）

> 本节仅列出需要改的“源头源码位置”，不涉及任何调试脚本或临时代码。

### 7.1 移除 `razel-mineru init`

- 取消 CLI 对 init 子命令的注册入口（`main.add_command(..., "init")`）
- `mineru/cli/init_config.py` 可保留文件但不暴露命令，或删除（以发行策略为准）
- 二开配置不再有任何自动生成/合并到用户 home 配置文件的行为

### 7.2 新增二开配置加载器（集中入口）

- 新增一个“只读加载器”，输入为 `--custom-config` 指定路径，输出为 `CustomConfig`（内含 enhance/storage/discard 三段）
- 加载器：
  - 只允许 YAML/JSON
  - 禁止 env 引用替换
  - 进行 schema 校验（Fail-fast）
  - 支持缓存（进程内只加载一次），但必须确保对“启动时固定配置”语义一致

### 7.3 调用链路显式传递 `CustomConfig`

需要将 `CustomConfig` 从入口透传至：

- CLI 本地解析：`do_parse(...)` / `_process_output(...)`
- FastAPI 请求处理：解析请求 options 后进入实际执行函数
- custom 模块：
  - enhance：`run_enhancement_pipeline(..., custom_config=...)`
  - storage：`build_output_writers(..., storage_options=custom_config.storage)`
  - discard：`resolve_discard_policy(..., discard_config=custom_config.discard)`

### 7.4 禁止二开读取 env / `~/mineru.json`

必须清理以下行为：

- 删除或废弃 `custom/config.py` 中“读取 `~/mineru.json` 的 enhance/storage/discard 段”的逻辑
- 删除 `bridge_enhance_to_env()` 及其在 `custom/registry.py` import 时的自动执行
- 删除二开相关 env fallback（包含 CLI/FastAPI 对 storage options 的 env 回退，以及 storage 内部对 `MINERU_S3_*` 的回退读取）

## 8. 行为矩阵（关键保证：原生不受影响）

### 8.1 CLI 行为矩阵

| 场景 | `--custom-config` | 二开是否介入 | 输出变化 |
|------|-------------------|--------------|----------|
| 原生模式 | 未提供 | 否 | 与当前原生 MinerU 完全一致 |
| 二开模式 | 提供 | 是 | 由配置文件决定：enhance/storage/discard 生效 |

### 8.2 FastAPI 行为矩阵

| 场景 | 启动参数 `--custom-config` | 二开是否介入 | 请求级是否可覆盖 |
|------|----------------------------|--------------|------------------|
| 原生服务 | 未提供 | 否 | 否（保持原生） |
| 二开服务 | 提供 | 是 | 否（本方案仅服务级固定配置） |

补充：**非 `md-only`（全量返回）模式下**，API 返回的 `results.zip` 必须包含 parse 目录下实际生成的全部产物文件（例如 `*_enhance.json`、`images.json`、可视化 PDF 等），避免因服务端打包白名单遗漏而导致“md 已增强但缺少 enhance.json”的不一致问题。

---

## 9. 落地顺序（最小风险路径）

为确保“修改完万无一失”，建议按以下顺序实施：

1. **先实现二开配置单一入口 + 显式传递**（二开仍可用，且不读 `~/mineru.json`/env）
2. **再移除 `razel-mineru init` 命令**（对运行时影响最小）
3. **最后清理所有二开相关 env fallback 与 `~/mineru.json` 回退链**（确保唯一配置源）
