# razel-mineru 打包部署与远程复用指南（Router 统一入口）

> 目标：你已经在 MinerU 上做了魔改（保持 Python 包名仍为 `mineru`），希望：
> - 统一对外使用 **`razel-mineru`** 命令
> - 你本地/机房可以用 Docker 部署服务
> - 他人只需安装一次客户端（或直接 curl），即可复用你的解析能力
>
> 本文覆盖三件事：
> 1) **他人如何安装你魔改后的 `razel-mineru`（客户端）**
> 2) **你如何部署服务端：两种 Router 形态**
> 3) **他人如何使用你的服务完成解析**

---

## 0. 重要概念：Router 接什么、客户端连什么

- **`razel-mineru-api`**：真正执行解析任务的 worker（对外 HTTP：`/health`、`/tasks`、`/file_parse`、`/tasks/{id}/result`）。
- **`razel-mineru-router`**：统一入口 + 调度层，对外暴露与 `razel-mineru-api` **一致**的 HTTP 接口。
  - Router 的 upstream **接入对象是 `razel-mineru-api`（8000）**，不是 `razel-mineru-openai-server`（30000）。
  - Router 只负责转发/调度，不关心 upstream 内部走 `pipeline` 还是 `vlm/hybrid`。

**对外推荐**：只对外暴露 Router（8002），worker（8000）放内网。

### 0.2 新增：只获取 Markdown 的轻量接口（推荐给外部用户）

在“只需要最终 Markdown（增强版）”的场景下，为避免下载 zip/解压目录结构，新增了一个轻量接口：

- `GET /tasks/{task_id}/md?file_name=<stem>`
  - **返回**：最终 `{stem}.md` 的文件流（`text/markdown; charset=utf-8`）
  - **特点**：不打包 zip、不需要客户端解压；适合跨网调用、Windows 一键保存
  - **多文件任务**：若一次任务包含多个文件，必须显式传 `file_name`

该接口与 `/tasks/{task_id}/result` 并存：
- 只要 md → 用 `/md`
- 要全量产物（md + json + images + ...）→ 用 `/result`（zip）

### 0.1 配置责任边界（重要）

- **服务端配置（你负责）**：增强相关 `MINERU_ENHANCE_*`、存储相关 `MINERU_STORAGE_OPTIONS_*` 等，都应在 **`razel-mineru-api/router` 启动时**通过环境变量或 `.env` 配置注入。
- **客户端/客户使用（对方负责）**：只需要拿到 `--api-url http://<YOUR_IP>:8002`（或 8000），以及传入解析入参（PDF 路径、输出目录等）。不应该要求客户设置你的增强/存储内部配置。

## 1) 他人如何安装你的魔改 `razel-mineru`（客户端）

你采用的是“方案 A”：**不改包名 `mineru`，只新增命令 `razel-mineru`**。

这意味着：他人安装到环境里后，会同时得到两个命令：
- `mineru`
- `razel-mineru`（你对外统一使用它）

### 1.0 关键说明：为什么 wheel 仍叫 `mineru-*.whl`

因为发行包名仍是 `mineru`（`pyproject.toml` 的 `[project].name` 未改），所以产物文件名仍形如：

```text
dist/mineru-<version>-py3-none-any.whl
```

但安装后会生成 **`razel-mineru`** 命令（由 `[project.scripts]` 提供）。因此：

- **交付给同学的文件名**：`mineru-*.whl`（这是正常/预期）
- **同学使用的命令**：统一用 `razel-mineru ...`

### 1.1 推荐交付方式：发 wheel（最稳、最可控）

你在自己的源码目录构建 wheel：

```bash
cd MinerU
chmod +x scripts/*.sh
./scripts/build.sh
ls -lh dist/*.whl
```

把 `dist/*.whl` 发给同学，同学在自己的虚拟环境里安装：

```bash
uv venv .venv
source .venv/bin/activate

uv pip install ./mineru-*.whl
razel-mineru -v
```

**注意**：因为包名仍是 `mineru`，若同学机器上已装官方版 `mineru`，请先在同一个 venv 里卸载旧版再装 wheel：

```bash
uv pip uninstall -y mineru
uv pip install ./mineru-*.whl
```

可选：如需发布到 PyPI（仅发布 wheel），先导出 token 再执行：

```bash
cd MinerU
export UV_PUBLISH_TOKEN="pypi-xxxx"
./scripts/publish_pypi.sh
```

### 1.2 备选：从 git 安装（适合内部仓库）

如果你把魔改代码放在公司 git 仓库（私有），同学可直接：

```bash
pip install "git+ssh://<your_git_repo>.git#subdirectory=MinerU"
razel-mineru -v
```

> 说明：这里仍然安装的是名为 `mineru` 的 Python 包，但脚本入口包含 `razel-mineru`。

### 1.3 本地自测（推荐用 uv，完全隔离）

用于你自己验证 wheel 是否“可安装 + 命令可用 + 不缺包”：

```bash
mkdir -p test/razel-mineru-verify
cd test/razel-mineru-verify

uv venv .venv
source .venv/bin/activate

uv pip install ../../MinerU/dist/mineru-*.whl
razel-mineru -v
```

> 提示：第一次运行 `razel-mineru -v` 可能会比较慢（首次 import 大量依赖 + 动态库加载 + 生成缓存），第二次通常明显变快。

### 1.5 存储配置的统一入口（推荐用环境变量 / `.env`）

如果你希望“客户不需要每次传 `--storage-options-*`”，建议把存储配置放在服务端进程环境里：

- `MINERU_STORAGE_OPTIONS_JSON`：直接放 JSON 字符串
- `MINERU_STORAGE_OPTIONS_FILE`：放 JSON 文件路径

规则：
- 两者只能二选一（同时设置会报错）
- **CLI 优先级**：若用户显式传了 `--storage-options-json/--storage-options-file`，会覆盖 env（便于临时覆盖）
- **服务端优先级**：若请求里没带 `storage_options_json`，服务端会用 env 兜底（便于统一默认）

示例（服务端启动前）：

```bash
export MINERU_STORAGE_OPTIONS_FILE="/Users/zhuanghengheng/multi-source-data-preprocess-pipeline/s3.json"
razel-mineru-api --host 0.0.0.0 --port 8000
```

> 这样客户侧只要 `--api-url http://<YOUR_IP>:8000` 即可，无需再传 storage options。

### 1.4 发布前必做检查：自定义目录必须是“可打包的 Python 包”

如果你在 `mineru/custom/<xxx>/...` 下新增了可被 import 的子目录（例如 `mineru.custom.storage`），务必确保该目录包含 `__init__.py`。

原因：当前工程使用 setuptools 且 `namespaces = false`，没有 `__init__.py` 的目录不会被识别为 package，从而 **打进 wheel 后缺包**，典型报错为：

```text
ModuleNotFoundError: No module named 'mineru.custom.xxx'
```

## 2) 你如何部署服务端（Docker）

### 2.0 开发期（不构建镜像）本地调试方式（外层 `.venv312`）

适用场景：
- 你还在频繁改代码
- 不想每次都 `docker build`
- 希望 VSCode/Debugpy 仍然沿用外层解释器（例如你的 `.vscode/launch.json` 指向 `${workspaceFolder}/.venv312/bin/python`）

#### 2.0.1 在外层 `.venv312` 做可编辑安装（关键）

在仓库根目录执行：

```bash
cd /Users/zhuanghengheng/multi-source-data-preprocess-pipeline
source .venv312/bin/activate

cd MinerU
uv pip install -e ".[core]"
```

说明：
- 必须用 `-e`（editable），这样你改动源码会立即生效
- 同时会把 `razel-mineru-api` / `razel-mineru-router` 等脚本安装到外层 `.venv312/bin/`

#### 2.0.2 本地启动并调试 API

```bash
razel-mineru-api --host 0.0.0.0 --port 8000
```

#### 2.0.3 本地启动并调试 Router（自动托管本机 worker）

```bash
razel-mineru-router --host 0.0.0.0 --port 8002 --local-gpus 0
```

> 若命令不存在，优先检查是否激活了外层 `.venv312`，以及是否已经执行过 `uv pip install -e ".[core]"`。

你仓库里已经支持用本地源码构建镜像，并提供两套 compose：
- `docker/compose.china.yaml`：基于 `docker/china/Dockerfile`（国内镜像/ModelScope）
- `docker/compose.global.yaml`：基于 `docker/global/Dockerfile`（全球源/HuggingFace）

镜像名统一为：`razel-mineru:latest`

### 2.1 构建镜像（China 示例）

```bash
cd MinerU
docker build -t razel-mineru:latest -f docker/china/Dockerfile .
```

验证镜像内命令存在（最小验证）：

```bash
docker run --rm -it razel-mineru:latest razel-mineru -v
docker run --rm -it razel-mineru:latest mineru -v
```

### 2.2 运行前置：关于 Colima 与 docker compose

如果你在 macOS 用 Colima：
- Colima 负责提供 Docker daemon（socket）
- `docker compose ...` 是否可用取决于你本机 Docker CLI 是否带 Compose 组件

常见做法（Homebrew）：

```bash
brew install docker docker-compose
colima start
```

然后检查：
- `docker version`
- `docker compose version`（或 `docker-compose version`）

## 3) 部署形态一：Router + 多台 GPU Worker（每台跑 api）

这是推荐的“可扩容”形态。

### 3.1 架构

- **入口机（你这台，Router）**：`razel-mineru-router`（对外 `:8002`）
- **GPU Worker 机器（多台）**：每台跑 `razel-mineru-api`（内网 `:8000`）
- （可选）每台 GPU Worker 机器本机跑 `razel-mineru-openai-server :30000`，供其 `api` 内部 VLM 推理使用

### 3.2 GPU Worker 机器启动（每台各自）

用 compose 起 api（China 例）：

```bash
cd MinerU
docker compose -f docker/compose.china.yaml --profile api up -d
```

对外（内网）健康检查：

```bash
curl http://<worker_ip>:8000/health
```

> 若你使用的是 `docker-compose`（带连字符），把命令替换为 `docker-compose -f ...`

#### 3.2.1（新增）Docker 部署时如何指定 `--custom-config`（推荐做法）

原则（非常重要）：
- **`--custom-config` 必须加在“实际执行解析”的进程上**，即每台 worker 的 `razel-mineru-api` 容器启动命令。
- **`razel-mineru-router` 若只是转发/调度 upstream**：不需要 `--custom-config`（由 worker 持有并生效）。
- **客户端（外部用户）不需要/不应该传 `--custom-config`**：只要 `--api-url http://<YOUR_IP>:8002`（router）或 `:8000`（api）。

做法 A：`docker run`（单机验证最直观）

```bash
docker run --rm -p 8000:8000 \
  -v "/abs/path/to/custom.yaml:/app/custom.yaml:ro" \
  razel-mineru:latest \
  razel-mineru-api --host 0.0.0.0 --port 8000 --custom-config /app/custom.yaml
```

做法 B：`docker compose`（长期部署推荐）

在 `docker/compose.china.yaml`（或 `compose.global.yaml`）的 `api` 服务里：
- **挂载** custom config 文件到容器内（只读）
- 在 `command:` 中给 `razel-mineru-api` **追加** `--custom-config /container/path/custom.yaml`

示例（概念片段，按你实际 compose 服务名合并）：

```yaml
services:
  api:
    image: razel-mineru:latest
    ports:
      - "8000:8000"
    volumes:
      - ./custom.yaml:/app/custom.yaml:ro
    command: ["razel-mineru-api", "--host", "0.0.0.0", "--port", "8000", "--custom-config", "/app/custom.yaml"]
```

> 备注：如果你要“一套镜像多环境复用”，建议把宿主机的 custom config 文件路径通过 compose 的环境变量注入（volume 的左侧），容器内路径保持固定（例如始终 `/app/custom.yaml`）。

### 3.3 入口机启动 Router，并接入多个 upstream

Router 的 upstream 指向各 worker 的 `razel-mineru-api`：

```bash
razel-mineru-router --host 0.0.0.0 --port 8002 \
  --upstream-url http://<worker1_ip>:8000 \
  --upstream-url http://<worker2_ip>:8000
```

（容器方式）也可以用 compose 起 router，但需要把上面 upstream 参数写进 `command:`。

## 4) 部署形态二：Router 在本机 + 自动拉起本机 worker（--local-gpus）

这是“单机多卡/单机快速落地”的形态：你只跑一个 router，它自己在本机拉起 worker 进程。

> 适用：你不想手动起 `razel-mineru-api`，希望 router 统一托管。

示例：

```bash
razel-mineru-router --host 0.0.0.0 --port 8002 --local-gpus 0
```

多卡示例（按实际 CLI 支持写法调整）：

```bash
razel-mineru-router --host 0.0.0.0 --port 8002 --local-gpus 0,1
```

**注意（显存）**：同机不要重复启动多个会预分配显存的 VLM 服务，否则容易 OOM。

## 5) 他人如何使用你的服务（统一用 razel-mineru）

他人只需要拿到你对外暴露的 Router URL（推荐）：

```text
http://<YOUR_IP>:8002
```

### 5.1 CLI 一条命令解析（推荐给同学）

```bash
razel-mineru -p <input_path> -o <output_path> -u http://<YOUR_IP>:8002
```

> 说明：只要 `-u` 指向你的 Router（或 API），解析实际执行发生在你的服务端（即你的魔改逻辑生效）。

### 5.1.1 只下载最终 Markdown（不下载 zip、不解压）——推荐新方式

当客户只需要最终增强版 `*.md` 时，推荐使用 CLI 的 `--md-only`：

```bash
razel-mineru -p <input_path> -o <output_path> --api-url http://<YOUR_IP>:8002 --md-only
```

行为：
- 仍然走 `/tasks` 异步任务（可轮询、可追踪）
- 任务完成后走 `/tasks/{id}/md?file_name=...` 下载 **md 文件流**并写入 `-o` 目录
- 如果服务端版本较旧（无 `/md` 接口，返回 404/405），CLI 会**自动回退**到 `/result` zip：
  - 回退时 zip **也只包含 md**（不会携带 middle/model/content_list/images 等）
  - 并且客户端只提取 `*.md` 写入输出目录

### 5.2 直接 HTTP 调用（不用装 CLI）

提交任务（异步）：

```bash
curl -X POST http://<YOUR_IP>:8002/tasks \
  -F "files=@demo1.pdf" \
  -F "return_md=true"
```

获取最终 Markdown（文件流，推荐）：

```bash
curl -L "http://<YOUR_IP>:8002/tasks/<task_id>/md?file_name=demo1" -o demo1.md
```

轮询状态 / 获取结果：

```bash
curl http://<YOUR_IP>:8002/tasks/<task_id>
curl http://<YOUR_IP>:8002/tasks/<task_id>/result
```

## 6) 对外发布前的检查单（强烈建议）

1. 服务监听是否是 `0.0.0.0`（否则外网/跨机访问不到）
2. 端口/安全组/防火墙是否放通：
   - 对外最少放通 `8002`（Router）
   - worker `8000` 建议仅内网可达
3. 健康检查：
   - `curl http://<YOUR_IP>:8002/health`
4. 同学侧验证：
   - `razel-mineru -p demo1.pdf -o out -u http://<YOUR_IP>:8002`

5. CLI 启动体验（可选优化项）：
   - 第一次执行慢属正常（首次 import/缓存），但如果你希望 `-v` 秒出，需要做“轻量 version path”优化（避免导入完整解析链路）。
