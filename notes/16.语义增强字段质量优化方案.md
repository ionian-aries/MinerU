## 1. 问题诊断

### 1.1 核心问题

当前两层增强（section 级 + doc 级）产出的内容**在同一个抽象层面上**——section summary 描述"这章讲了什么"，doc_outline_insights 也在描述"这章讲了什么（缩短版）"。这不是两层语义增强，而是一层内容的两份拷贝。

### 1.2 实际输出证据（demo1 论文）

**对比 doc_outline_insights vs sec_003 summary**：

| doc_outline_insights | sec_003 summary |
|---|---|
| "植树造林显著改变了流域的蒸散发，尤其在年降雨量超过400-500毫米时差异更为明显" | "广泛的植树造林…显著改变了流域的蒸散发（ET）…尤其在年降雨量超过400-500毫米时差异更为明显" |

几乎 1:1 复述。insight 只是从 section summary 中抽了一两句出来。

**对比 main_idea vs summary**：

| main_idea | summary |
|---|---|
| "本章节详细描述了流量分析的方法，重点在于流量持续曲线的构建及其与植树造林和降雨的关系" | "本章节介绍了流量持续曲线（FDC）的构建方法…采用S形函数描述植被生长对流量的影响…" |

main_idea 是 summary 的缩短版，没有从"描述"上升到"论断"。

**section keywords 跨节区分度低**：

| sec_001 keywords | sec_003 keywords | sec_004 keywords |
|---|---|---|
| 植树造林, 流量持续曲线, 气候信号… | 植树造林, 蒸散发, 流量持续曲线… | 流量持续曲线, FDC, 降雨, 植被特征… |

"植树造林""流量持续曲线"出现在几乎所有 section 的 keywords 中，BM25 检索时无区分度。

### 1.3 根因分析（三条）

1. **Section prompt 未要求自包含**：summary 可以写"本章节…"这种依赖标题才能理解的描述
2. **Section prompt 未区分 summary vs main_idea 的语义分工**：两者的唯一区别是长短，不是维度
3. **Doc prompt 未给出 section 层 vs doc 层的精确对比定义**：上午已修复（给了 positive/negative 示例），但 section prompt 配套优化尚未做

## 2. 设计哲学：Retrieval-Oriented Dual-Layer Enrichment

### 2.1 业界参考依据

| 项目/论文 | 核心思想 | 与本方案的关系 |
|-----------|---------|---------------|
| **LlamaIndex Hierarchical Indices** + **Document Summary Index** | 先 summary 级别检索，再 drill down 到 chunk；检索用的表示和生成用的表示应解耦 | section summary 作为检索入口，refs 指向原文 chunk 用于生成 |
| **LlamaIndex Production RAG Guide** | "Decouple chunks used for retrieval vs. chunks used for synthesis" | 直接印证两层增强的分工逻辑 |
| **LangChain Multi-Vector Retriever** | 用 summary/proposition 做检索入口，用原文 chunk 做生成上下文 | doc_outline_insights 即命题级检索入口，section_id 指向详细上下文 |
| **LightRAG** (HKUDS, arXiv:2410.05779) | Dual-level retrieval: low-level entity + high-level theme | section keywords = low-level, doc insights = high-level |
| **Proposition Chunking** (arXiv:2312.06648, Tony Chen et al.) | 把文本分解为 atomic、factual、self-contained 的命题，命题作为检索单元 | main_idea 应是命题式 claim；doc_outline_insights 的每条也是独立命题 |
| **RAG Survey** (arXiv:2312.10997) | 检索增强生成的系统性综述，覆盖 chunking 策略与多路召回 | 验证 keyword 扩展策略的合理性 |
| **RAG Failure Points** (arXiv:2401.05856) | RAG 系统的 7 个失败点，包括 chunking 和检索质量 | 验证 self-contained summary 对避免检索遗漏的重要性 |

### 2.2 两层增强服务于不同检索阶段

```
用户 Query
    ↓
阶段 1: 文档级路由/过滤/排序
    消费字段: global_summary + global_keywords + doc_outline_insights
    回答问题: "哪篇文档可能有答案？"
    ↓
阶段 2: 章节级定位
    消费字段: section summary + keywords + main_idea
    回答问题: "文档中哪个章节最相关？"
    ↓
阶段 3: 原文 chunk 获取
    消费字段: refs 指向原始 block
    回答问题: "把原文拿出来给 LLM 生成回答"
```

两层增强的根本分工不是「简 vs 详」，而是**服务于不同的检索阶段**。

## 3. Section 级增强：三字段优化方案

**原则**：字段名不改（`summary`、`keywords`、`main_idea`），Schema 不改，只改 prompt 质量标准。

### 3.1 `summary` — 检索锚点

**当前状态**：summary 依赖标题才能理解，包含"本章节…""如前所述…"等指代。

**优化后定义**：自包含（self-contained）检索向摘要。

**质量标准（写进 prompt 的硬约束）**：

| 维度 | 要求 |
|------|------|
| **自包含性** | 读这段 summary 的人不知道文档标题、不知道这是哪个章节，也能准确理解它在说什么。禁止"本章节…""本节…""如前所述…"等依赖上下文的表述 |
| **实体保留** | 专业术语保留原文形式，中英文都保留（如"流量持续曲线（FDC, flow duration curve）"） |
| **数值保留** | 关键数值/条件/阈值不丢失（如"年降雨量超过 400-500mm 时"） |
| **信息完整** | 可含方法步骤、数据细节、实验结果要点——信息密度越高越好 |
| **检索友好** | summary 文本将被 embedding 后用于向量检索，需包含足够的语义信号 |

**设计依据**：Proposition Chunking（arXiv:2312.06648）的核心原则——每段描述必须脱离上下文也能完全理解。LlamaIndex Production RAG Guide 第一原则——检索用的表示要独立可用。

**优化前后对比（sec_004 "2. Methods"）**：

| | 优化前 | 优化后期望 |
|---|---|---|
| summary | "本章节介绍了流量持续曲线（FDC）的构建方法，基于每日流量数据分析流量与时间百分比的关系，强调降雨对流量的影响…" | "在植树造林水文效应的量化分析中，流量持续曲线（FDC, flow duration curve）通过将每日流量按超越概率排序来刻画流域的流量分布特征。本研究采用 S 形函数（sigmoidal function）描述林龄增长对流量的渐进影响，并引入逆 S 形函数量化造林对零流量天数（zero-flow days）的作用——降雨量增加时零流量天数减少，而造林则显著增加零流量天数。模型拟合优度以效率系数 E 评判，通过 t 检验确认降雨和林龄对流量变化的统计显著性。" |

关键差异：优化后不再以"本章节"开头，直接用实体名展开；保留了"S形函数""逆S形函数""效率系数E""零流量天数"等具体术语；脱离标题也完全可理解。

### 3.2 `keywords` — 多路召回扩展词表

**当前状态**：不同 section 的 keywords 高度雷同，跨节通用词过多。

**优化后定义**：三类词策略 + 去除跨节通用词。

**三类词结构**：

| 类型 | 说明 | 占比建议 | 示例（sec_004 "2. Methods"）|
|------|------|---------|--------------------------|
| **实体词** | 本节出现的专有名词/术语/数据集名/公式名 | ~40% | "FDC""效率系数E""零流量天数""t检验" |
| **方法词** | 本节涉及的方法/工具/模型/技术 | ~30% | "S形函数建模""逆S形函数""流量超越概率""sigmoidal function" |
| **扩展词** | 同义词/缩写/用户可能的其他说法 | ~30% | "flow duration curve""模型拟合优度""goodness of fit""降雨-径流分析" |

**硬约束（写进 prompt）**：

1. 至少 6 个，建议 8-10 个
2. **禁止出现文档主题通用词**（如"植树造林""水文影响"——这些几乎每个 section 都适用，应由 global_keywords 承担）
3. 每个 keyword 都必须是本节独有或重点涉及的概念
4. 扩展词只扩展本节实际涉及概念的同义词，不外推文中未提及的概念

**关于扩展词准确性的评估**：

扩展词本质上是 query expansion（LangChain Multi-Query Retriever 的核心策略）。在 RAG 多路召回中：
- keywords 提高**召回率**（用户用不同说法也能命中）
- summary embedding 保证**精确率**（向量相似度做二次过滤）

因此扩展词适度放宽是安全的，准确性由向量检索兜底。

### 3.3 `main_idea` — 命题式论断

**当前状态**：是 summary 的缩短版，信息完全重叠。

**优化后定义**：一个可被验证的 claim（命题），不是内容描述。

**关键区分**：

| | 内容描述（当前） | 命题 claim（优化后） |
|---|---|---|
| 句式 | "本节介绍了…""本章描述了…" | 判断句/论断句 |
| 回答的问题 | "这一章做了什么" | "这一章论证/发现了什么" |
| 与 summary 的关系 | summary 的子串/缩短版 | 与 summary 互补——summary 说"怎么做的+结果是什么"，main_idea 说"这意味着什么" |

**优化前后对比（sec_004 "2. Methods"）**：

| | 优化前 | 优化后期望 |
|---|---|---|
| main_idea | "本章节详细描述了流量分析的方法，重点在于流量持续曲线的构建及其与植树造林和降雨的关系" | "S形函数与逆S形函数的组合可以有效解耦降雨变异性和植被生长对流量持续曲线的各自贡献" |

**设计依据**：Proposition Chunking 强调 atomic、factual、self-contained 的命题是最佳检索单元。main_idea 就是本节最核心的那一个 proposition。

## 4. Doc 级增强：三字段优化方案

**原则**：字段名不改（`global_summary`、`global_keywords`、`doc_outline_insights`），Schema 不改。doc_summary.j2 上午已做重大改版（增加 positive/negative 示例 + 抽象层级定义），本次做微调。

### 4.1 `global_summary` — 文档级向量入口

**当前状态**：基本合格，但不同文档的结构差异大，有时过于罗列细节。

**优化方向**：增加四段式结构约束（写进 prompt）。

**四段式结构**：

```
[研究问题] 本研究探讨了…的问题/挑战
[方法路径] 采用…方法/提出了…框架
[核心发现] 结果表明…/发现了…
[意义与边界] 这对…领域具有…意义；但在…方面存在局限
```

**说明**：不要求 LLM 输出这四个标签，而是在 prompt 中要求 summary 必须覆盖这四个维度。这样：
- 文档级向量表示稳定、信息密度均匀
- 不同类型文档（论文/报告/法规/手册）都适用
- 用户无论从"问题""方法""结论""意义"哪个角度提问，都有命中信号

### 4.2 `global_keywords` — 文档级主题标签

**当前状态**：跟 section keywords 高度重叠。

**优化方向**：明确与 section keywords 的分工（写进 prompt）。

**分工规则**：

| 维度 | section keywords | global_keywords |
|------|-----------------|-----------------|
| **粒度** | 本章独有的实体/方法/术语 | 全文主题/领域/跨章节概念 |
| **作用** | 区分章节间的差异 | 文档级过滤/聚类/领域路由 |
| **典型内容** | "S形函数""Coalburn流域""效率系数E" | "水文学""造林水文效应""流域管理""土地利用变化""flow regime analysis" |

**合理衍生的边界**：

| 类型 | 示例 | 判断依据 |
|------|------|---------|
| ✅ 合理 | 从 "afforestation" 衍生 "land use change" | 上位概念，文中隐含讨论 |
| ✅ 合理 | 从 "FDC" 衍生 "flow regime analysis" | 领域术语，直接相关 |
| ❌ 不合理 | 衍生 "climate change" | 文中明确说是去除气候信号，不是研究气候变化 |
| ❌ 不合理 | 衍生 "machine learning" | 文中未使用任何 ML 方法 |

**标准**：衍生词必须是文中内容的合理上位概念或领域归属，不能是文中未涉及的外延主题。

### 4.3 `doc_outline_insights` — 命题级检索入口

**当前状态**：上午已重写 doc_summary.j2（增加 positive/negative 示例 + 抽象层级定义），并新增 `_outline_looks_like_summaries()` 退化检测。

**本次补充明确**：与 section 级字段的精确分工表。

| | section summary | section main_idea | doc_outline_insights |
|---|---|---|---|
| **粒度** | 章节级 | 章节级 | 文档级 |
| **内容维度** | 这章做了什么、怎么做的（过程+细节） | 这章论证/发现了什么（核心命题） | 这篇文档的核心贡献/价值是什么（鸟瞰洞察） |
| **视角** | 节内视角 | 节内视角 | 跨章节、全文视角 |
| **检索场景示例** | 用户问"FDC 怎么构建的" | 用户问"S形函数有什么用" | 用户问"有没有方法能在非配对场景下评估植被水文效应" |
| **与其他字段的关系** | — | 不应是 summary 的子串 | 不应复述任何 section 的 summary 或 main_idea |

**section_id 指向规则**：

每条 insight 的 `section_id` 指向**最相关的证据来源章节**。一条 insight 可以综合多章信息（这是它"跨章节"的核心价值），但 section_id 指向最核心的证据来源。下游检索链路：

```
用户 Query → 向量检索命中某条 insight → 通过 section_id 获取对应 section → 获取 refs 指向的原文 chunk → LLM 生成回答
```

## 5. 明确不做的事

### 5.1 不新增字段

以下字段在调研中被评估过，当前阶段明确不加：

| 候选字段 | 评估结论 | 原因 |
|---------|---------|------|
| `hypothetical_queries` | 不加 | HyDE 的逆向应用，ROI 高但最佳实施层面是下游检索系统的 indexing 阶段，不是文档增强阶段 |
| `entities` | 不加 | 知识图谱抽取（如 LightRAG 的方式）应作为独立 Stage，不应混入 section summary 的职责 |
| `document_type` | 不加 | 文档类型标签应在 InputStage 或更上游确定，不属于 LLM 增强范畴 |
| `domain_tags` | 不加 | 可由 global_keywords 的上位词覆盖，无需独立字段 |
| `key_claims` | 不加 | 与 doc_outline_insights 功能重叠 |
| `self_contained_summary` | 不加 | 直接优化现有 summary 使其自包含，无需新建字段 |

**决策依据**：当前三个字段的质量问题（summary 不自包含、keywords 无区分度、main_idea 复述 summary、insights 复述 section）是最大的检索瓶颈。把现有字段做对，比加新字段收益大得多。每多一个字段 = 更长的 prompt = 更多 token 消耗 + 更多输出解析风险。

### 5.2 不改的代码/结构

| 项目 | 说明 |
|------|------|
| `schema.py` | 字段名和类型全部不变：`SectionEnhanceModel(summary, keywords, main_idea)`、`DocOutlineInsightItem(text, section_id)`、`DocEnhanceModel(global_summary, global_keywords, doc_outline_insights)` |
| `pipeline.py` | 7 阶段编排不变 |
| `stages_validate.py` | 校验逻辑不变 |
| `stages_compose.py` | 输出格式不变 |
| `stages_section_build.py` | 树构建逻辑不变 |
| `stages_token_estimation.py` | Token 估算不变 |
| `stages_section_enhance.py` | 调度逻辑不变（Mode A/B/C） |
| `stages_doc_enhance.py` | 上午加的退化检测保留，不做额外改动 |
| 输出格式 | `enhance.json` 和 `enhanced.md` 的结构完全不变 |

## 7. 验证方案

### 7.1 端到端验证（demo1）

改完 prompt 后，用 demo1 重新跑完整 pipeline，对输出 `demo1_enhance.json` 逐项检查：

| 检查项 | 标准 | 判定方法 |
|--------|------|---------|
| Section summary 自包含性 | 遮住标题，只看 summary，能否准确理解该节在说什么 | 人工审读 |
| Section keywords 区分度 | 不同 section 的 keywords 交集占比 ≤30% | 计算任意两节 keywords 的 Jaccard 系数 |
| main_idea vs summary 去重 | main_idea 不应是 summary 的子串或缩短版 | 检查 main_idea 是否出现在 summary 中 |
| main_idea 命题性 | main_idea 是判断句/论断，不是描述句（"本节介绍了…"） | 人工审读 |
| doc_outline_insights vs section summary 去重 | 每条 insight 与对应 section 的 summary 的 4-gram 重叠率 <50% | `_outline_looks_like_summaries()` 退化检测（已实现） |

### 10.5 关键技术判断

现有三字段的质量问题是 **prompt 指令不精确**导致的，不是 schema/pipeline/代码逻辑的问题。字段名、数据结构、处理流程全部正确，只是 LLM 在模糊指令下产出了低质量内容。

- prompt 模板中给出明确的质量标准、正反示例、硬约束（如"禁止'本章节'"）

## 11. Prompt 体系批判性评审与精准优化 (2026-04-22)

### 11.1 背景

对 §10 落地的 prompt 模板体系进行全面审视，识别出 7 项潜在优化点，逐一做第三方批判性评估后，确认仅 2.5 项值得在 MVP 阶段落地。

### 11.2 评审的 7 项问题及结论

| # | 问题 | 最初提案 | 批判结论 | 最终做法 |
|---|------|---------|---------|---------|
| 1 | P1(`section_summary.j2`) 与 P2(`section_batch_summary.j2`) ~49% 行重复 | `{% include %}` 抽公共 partial | ❌ **过度设计**。P2 只有 P1 的 58% 大小，精简是有意的（batch 模式省 token 以多装 section）；引入 include 会破坏 fallback renderer（`prompts.py` 无 jinja2 时仅支持 `{{ var }}` 替换）；两模板仅 1 次 commit，变更频率极低 | 加 `{# 同步注释 #}` |
| 2 | System prompt 三种管理方式混用（.j2 模板 / Python 常量 / 内联字符串） | 全部统一为 .j2 模板文件 | ❌ **工程审美驱动**。三个硬编码 system prompt 均极短（≤136 chars）、无变量、不需模板渲染；搬到 .j2 文件增加 I/O 和目录碎片，无功能性收益 | DocEnhance 内联字符串→模块顶部命名常量 `_DOC_SYSTEM_PROMPT` |
| 3 | Schema hint 追加在 prompt 末尾位置不语义连贯 | 移入模板内 `## 输出格式` 区域 | ❌ **修复了不是 bug 的东西**。末尾位置利用 LLM recency bias；~60 chars 影响微乎其微；移入模板需 `{{ schema_hint }}` 变量 + 条件分支，fallback renderer 不支持 | 改拼接前缀措辞为中文（`你的输出必须严格匹配以下JSON结构：`） |
| 4 | DocEnhance 4 段 retry prompt 共 1193 chars 硬编码在业务逻辑中间 | 提取为 Jinja2 模板条件块 `{% if retry_mode %}` | ❌ **拆散了检测-修补的内聚性**。retry 文字与退化检测逻辑紧耦合（`_outline_looks_like_titles()` → 追加标题约束），分离到模板文件降低内聚性；模板变成 5 分支状态机 | 提取为模块顶部 4 个命名常量 |
| 5 | "summary 必须自包含"规则在 system prompt 和 user prompt 中重复 | 去掉 system prompt 中的重复规则 | ❌ **风险收益不对称**。节省 ~73 tokens/call（总量 0.5-2%），但可能降低小模型关键规则遵守率；Anthropic 指南："if a rule is critical, reinforce it in multiple places" | 不改 |
| 6 | `max_words` 等参数硬编码，未暴露到配置文件 | 暴露 `prompt_params` 到 YAML | ⚠️ **方向对但过早**。`max_words` 改动需同步调 prompt 正例（正例长度基于 300 字设计），暴露了反而是配置陷阱 | MVP 不暴露，保持代码内默认值 |
| 7 | `section_plan.j2` 缺少 few-shot 示例 | 加 1-2 个正反例 | ✅ **真正有价值**。SectionPlan 是 pipeline 中校验失败率最高的阶段，小模型对"连续兄弟节点"约束看示例比读规则有效 | 加 1 个通用示例（短节合并 + 长节独立） |

### 11.3 核心教训

1. **不是所有"不一致"都需要修** — 只有造成真实问题（bug、输出质量下降、开发者犯错）的不一致才值得改
2. **fallback renderer 兼容性是硬约束** — 引入 Jinja2 控制流会把 jinja2 从可选依赖变成硬依赖
3. **LLM prompt 中关键规则重复是加固手段** — 对小模型尤其重要，不是冗余
