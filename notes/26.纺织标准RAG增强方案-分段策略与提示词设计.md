## 1. 文档结构分析

### 1.1 文档类型分类

资料库 9 份文档可分为两大类，结构差异显著：

#### A 类：产品标准（7 份）
> FZ/T 73020-2019、FZ/T 81006-2017、FZ/T 62013-2019、FZ/T 73018-2021、GB 18383-2007、GB/T 14272-2021、GBT 18132-2016

**固定章节结构**：
```
前言（修订历史、起草单位、与上版差异）
1. 范围（适用产品、适用场景、排除范围）
2. 规范性引用文件（参考标准清单）
3. 术语和定义（产品分类术语、专业名词）
4. 产品分类/规格（可选）
5. 技术要求
   5.x 原材料要求
   5.x 内在质量（核心：大型多维度表格，指标×等级×测试方法）
   5.x 外观质量（疵点等级表格）
   注脚/附注（豁免条款，极其重要！）
6. 试验方法（每个指标对应一个或多个操作步骤）
7. 检验规则（抽样方案、判定规则）
8. 标志、标签、包装
附录 A/B/C（规范性附录：补充测试方法；资料性附录：评价参考）
```

**关键特征**：
- 技术要求表格是信息密度最高的部分，跨越 优等品/一等品/合格品 三个等级
- 豁免/不考核条款分散在表格脚注（如"注1: 当...时，本项不考核"）
- 引用标准数量多（20-30 个），跨多个 GB/T 体系

#### B 类：试验方法标准（2 份）
> GBT 18319-2019（光蓄热）、GBT 21655.2-2019（吸湿速干动态水分传递法）

**固定章节结构**：
```
前言
1. 范围
2. 规范性引用文件
3. 术语和定义
4. 原理（测试方法的物理/化学原理）
5. 仪器与设备（精确技术规格，含图）
6. 试剂/材料（如需）
7. 样品制备/调湿
8. 试验步骤（详细操作流程）
9. 结果计算（公式 + 修约规则）
10. 评定/分级（通过/不通过阈值，分级表）
11. 试验报告（需记录的字段）
附录（仪器结构图、数据采集电路图）
```

**关键特征**：
- 核心是"仪器规格 + 操作步骤 + 计算公式"三件套
- 评定标准通常有明确的分级表（1-5 级）
- 计算公式多（3-7 个），修约规则明确

## 2. 问答集分析：检索需求建模

### 2.1 问题类型分布（175 条）

| 问题类型 | 数量 | 占比 | 典型问题 |
|----------|------|------|----------|
| **指标阈值查询** | 74 | 42% | "优等品耐皂洗色牢度标准值是多少？" "水洗尺寸变化率允许偏差？" |
| **试验步骤查询** | 44 | 25% | "拼接互染的试验步骤是什么？" "充绒量检验步骤？" |
| **术语定义查询** | 26 | 15% | "莱赛尔是规范名称吗？" "ALPACA是规范署名？" |
| **豁免/不考核** | 14 | 8% | "哪些情况下不考核？" "豁免条件是什么？" "缝子纰裂豁免条件？" |
| **适用范围查询** | 10 | 6% | "针织休闲服装适用什么标准？" "30个月婴儿用哪个标准？" |
| **文档元信息** | 7 | 4% | "起草单位是谁？" "新版相比旧版有什么变化？" |

**关键发现**：
1. **指标阈值查询占 42%**，是最高频需求，且通常同时涉及"产品等级 × 具体指标 × 测试方法"三个维度
2. **豁免条款查询占 8%**，但极易遗漏（豁免信息隐藏在表格脚注中），是召回失败的高风险区
3. **跨标准比较查询**（如 Q105-112、Q136-140）要求同一指标在不同标准中的信息可以被联合检索

### 2.2 检索失败的高风险场景

**场景一：分级表被拆分**
- 问题："合格品的耐摩擦色牢度标准值是多少？"
- 失败原因：如果一张表中优等品/一等品/合格品的行被分到不同 chunk，问题只能召回优等品行，无法回答合格品
- **要求：整张要求表必须在同一 section，不得拆分**

**场景二：豁免条款未提取**
- 问题："GB/T 2664-2017 中缝子纰裂的豁免条件是什么？"
- 失败原因：豁免信息在表格的脚注里（注2: 当面料为粗梳毛...不考核），embedding 相似度低
- **要求：豁免条款必须作为独立的可检索单元，并在增强时用直白语言显式提取**

**场景三：试验步骤被截断**
- 问题："针织休闲服装里拼接互染的试验步骤是什么？"
- 失败原因：如果试验步骤被按段落切分，一次召回只能返回部分步骤
- **要求：一个测试项目的完整流程（仪器+试剂+步骤+计算）必须在同一 section**

**场景四：术语定义语境丢失**
- 问题："黄麻是规范名称吗？能直接用于报告吗？"
- 失败原因：术语是否"规范"取决于 GB/T 4146.1，普通向量相似度无法判断
- **要求：定义类增强必须明确标注"规范名称/非规范名称"，并给出规范名**

## 4. 通用 section_type 分类体系

### 4.1 设计原则

section_type 不绑定任何文档领域，而是描述**内容块的首要语义功能**。同一份文档中不同章节可能具有完全不同的语义功能，LLM 的任务是根据内容的实际性质推断最合适的类型，而非套用领域预设。

**适用范围**：标准、论文、手册、法规、报告、方案等各类结构化文档。

### 4.2 九种通用类型

| section_type | 首要语义功能 | 典型信号（跨领域） | 增强动作 |
|-------------|------------|----------------|---------|
| `meta` | 文档的身份与溯源信息：谁写的、何时发布、与其他版本的关系 | 前言、版本号、作者单位、修订历史、摘要行政信息 | minimal |
| `scope` | 文档的覆盖边界：适用什么、不适用什么、面向谁 | 范围章节、适用条件、排除说明、目的陈述 | enhance |
| `concept` | 陈述"事物是什么"：定义、分类、概念、术语体系 | 术语和定义、名词解释、符号说明、分类表 | enhance |
| `requirement` | 陈述"事物必须满足什么"：规则、约束、规范性指标 | 技术要求、性能指标、合格准则（常含多维度表格） | enhance |
| `procedure` | 陈述"如何做"：操作步骤、方法、工作流、算法 | 试验步骤、操作规程、实施方法、处理流程 | enhance |
| `evaluation` | 将测量结果映射到判断：分级、判定、评定、结论依据 | 判定规则、分级标准、合格/不合格条件、评分表 | enhance |
| `reference` | 指向外部知识源：引用清单、文献、参考文档 | 规范性引用文件、参考文献、附录目录 | minimal |
| `narrative` | 解释性/背景性叙述：动机、背景、讨论、说明性附录 | 引言、背景、讨论、结论、资料性附录 | enhance |
| `title_only` | 纯导航节点，无实质性内容 | 只含标题行、无正文 | skip |

### 4.3 几点说明

**关于 `requirement` 的表格与例外条款**

`requirement` 类型是信息密度最高、召回价值最大的类型。当一个 requirement 节同时包含"主体规范指标"和"例外/豁免条件"时：
- 若豁免条件嵌入表格脚注或少量文字，保留在同一 section 内
- 若豁免条件形成独立子章节，且体量足以独立召回，则拆出作为独立 section（类型仍为 `requirement`，但 enhance_guidance 专注于例外条件提取）

**关于 `procedure` 的完整性**

一个测试项目/操作规程的"仪器设备 + 操作步骤 + 结果计算"在语义上是不可分割的——仅有步骤而无仪器规格无法执行，仅有步骤而无计算公式无法得出结论。若这三者属于同一操作场景，应划入同一 section。

**关于 `concept` 的粒度**

单个术语/定义通常过短，无法独立召回。应将语义相近或同属一个概念体系的若干术语合并为一个 section，以获得足够的语义密度。

### 4.4 视觉元素（图片/表格）的处理

一个 section 中可能包含图片和表格。处理原则：

**同一 section 内的图片/表格与文字一起处理**：
- 表格的 HTML 结构和图片的 caption/alt 文字已在 body_text 中以文本形式呈现（来自 BlockIndexer 的渲染规则）
- 表格 HTML 保留了行列关系，文本 LLM 可以理解多维度数据
- 图片的 caption 提供语义锚点，结合上下文可推断图片内容

**视觉密集节的标记**：
- `image_count > 0` 或 `table_count > 0` 的 EnhanceUnit 在 enhance_guidance 中应说明视觉元素的存在
- enhance_guidance 示例："本节含 N 张表格，表格的行列关系是核心语义，请基于表格内容提取各维度的关系命题"

**Phase 2 多模态扩展**（预留）：
- 对于图表内容复杂（如工程图纸、显微镜图像、实验装置图）且 caption 语义不足的情况，后续引入 VLM 辅助
- VLM 处理时 section 的文字上下文作为 prompt context 一并传入，保证理解完整性
- 当前 Phase 1：table HTML + 图片 caption + 周边文字 = 足够的语义信息

## 5. Section Plan LLM 提示词

### 5.1 System Prompt（section_plan_sys.j2）

设计原则：**只给抽象指导原则，不携带任何领域知识**。LLM 凭借通用理解推断文档结构，再依据原则做分段决策。

```
你是文档结构分析专家。你的任务是：将给定文档的内容块序列，划分为最优的 RAG 检索单元，
并为每个检索单元指定语义类型和增强指导意见。

## 文档类型推断
首先根据文档标题和内容特征，用简洁的语言描述当前文档的类型与用途。
不要套用预设分类，而是根据文档实际呈现的结构和内容来描述。

## 分段核心原则

### 不可拆分的情形
以下情形中，相关内容块必须归入同一 section：

1. **多维关联内容**：当若干内容块共同构成一个多维度的整体（例如一张表格的不同行/列），
   任何单行或单列单独存在都会丧失语义完整性，必须保持在同一 section。

2. **顺序依赖内容**：当内容块之间存在显式或隐式的顺序依赖（后续步骤依赖前序步骤的
   结果、先决条件、上下文），拆分后将导致任一部分无法独立使用，必须保持完整。

3. **问答单元不可分**：若一组内容块在检索时总是需要整体才能回答某类问题（例如，
   一个测试方法的"仪器"+"步骤"+"计算"缺一不可），应视为一个检索单元。

### 必须独立成节的情形
以下情形中，相关内容块应从周边内容中分离，独立成节：

1. **语义功能截然不同**：若某内容块的"回答什么类问题"与周边内容根本不同
   （如"是什么"类 vs "如何做"类 vs "必须满足什么"类），应独立成节。

2. **高价值独立查询点**：若某类内容会被用户单独、独立地查询（例如例外条件、
   边界条件、特殊说明），即便内容量少，也应独立成节以提高召回精度。

3. **来源/溯源信息**：文档的行政元信息（发布信息、版本差异、引用关系等）
   与正文内容功能不同，应独立成节。

### 允许合并的情形
以下情形可将多个小内容块合并为一个 section：

1. **内容过短**：单个内容块语义密度过低、不足以作为独立检索单元时，
   可与相邻、语义相近的内容块合并。

2. **同功能相邻块**：相邻的多个内容块具有相同的语义功能，且合并后
   token 量仍在合理范围内，可合并为一个更充实的检索单元。

3. **过渡性文字**：章节引言、过渡说明等不独立承载检索价值的文字，
   可并入其主体内容的 section。

## section_type 赋值指南
section_type 描述该 section 的首要语义功能，使用以下类别之一：

- meta：文档身份与溯源（发布信息、版本历史、作者等）
- scope：文档的适用范围与边界
- concept：陈述"事物是什么"（定义、术语、分类、理论基础）
- requirement：陈述"必须满足什么"（规范指标、约束条件、合格要求，常含表格）
- procedure：陈述"如何操作"（步骤、方法、工作流、算法）
- evaluation：将结果映射到判断（分级、判定规则、评定标准）
- reference：指向外部知识源（引用列表、参考文献）
- narrative：背景、解释、讨论等支撑性叙述
- title_only：仅有标题，无实质内容

## enhance_guidance 写作要求
为每个 section 写一条指导意见，说明增强 LLM 在处理该 section 时，
应重点关注什么、提取什么形式的信息、有哪些潜在的信息遗漏风险。

enhance_guidance 应：
- 基于该 section 内容的实际特征（密度、结构、维度数）来写
- 描述"应提取什么"而非"怎么提取"
- 指出该节内容在检索时的典型查询模式
- 不超过 3 句话
```

## 6. 各 section_type 增强提示词

每种类型对应一个 j2 模板，模板设计原则：**描述"该提取什么形式的信息"，不携带领域预设**。模板变量通过 manifest.yaml 的 output_schema 注入（数量约束、字段要求），增强 LLM 只需关注内容层面的提取策略。

### 6.1 meta 类型

**检索场景**：文档溯源、版本对比、"谁写的/什么时候发布的/改了什么"类查询

**enhance_guidance 示意**（Section Plan LLM 生成）：
> "本节包含文档的身份与版本信息，请提取所有结构化的行政元数据，并将版本间的变化整理为对比性陈述，以支持'新旧版本差异'类查询。"

**增强提示词核心逻辑**（meta_enhance.j2）：
```
提取该文档节的身份与溯源信息，输出：
- summary：用一段话描述文档的身份（标准号/文件名）、发布信息、以及与历史版本的关键差异
- keywords：包含文档编号、发布年份、负责机构/单位名称、关键变化描述词
- main_idea：本版本相比历史版本最重要的一项变化（若无历史版本，则陈述文档的核心定位）
- questions：能从本节直接回答的查询，优先覆盖"何时发布/谁负责起草/相比上版有何变化"类

附加字段 doc_metadata（结构化提取）：
- 标准编号 / 文件名
- 发布日期、实施日期
- 负责/起草机构
- 代替的历史版本（若有）
- 本版本主要变化条目列表
```

---

### 6.2 scope 类型

**检索场景**："哪类产品/场景适用本文件"、"X 是否在本标准范围内"类查询

**增强提示词核心逻辑**（scope_enhance.j2）：
```
提取该文档节的适用范围与边界信息，输出：
- summary：明确说明本文件适用的对象（产品/材料/方法/人群）、适用条件，
  以及明确排除的情形（若有）
- keywords：涵盖所有适用对象的名称、关键限定条件、排除项描述词
- main_idea：一句话概括本文件最核心的适用对象
- questions：覆盖"X 是否适用本文件"、"本文件适用哪类场景"等选标准/判适用类查询

附加字段：
- applicable_to：适用对象与条件的完整描述
- excluded：显式排除的对象或场景（若原文未明确排除，填"未作明确排除"）
```

---

### 6.3 concept 类型

**检索场景**："X 是什么"、"X 和 Y 的区别"、"X 的定义是什么"类查询

**增强提示词核心逻辑**（concept_enhance.j2）：
```
提取该文档节定义或描述的概念，输出：
- summary：说明本节定义了哪些类别的概念，它们之间是否有层级或关联关系
- keywords：包含所有被定义概念的名称（含同义词/英文名若有）
- main_idea：本节最核心的一个概念定义（一句话）
- questions：覆盖"X 的定义是什么"、"X 是否是规范/标准名称"、"X 属于哪个类别"类查询

附加字段 term_entries（逐条提取）：
- 概念名称（正式名）
- 定义文本（完整）
- 补充说明/备注（若有）
- 别名或同义词（若有）
- 与其他概念的关系（若有上下位关系）
```

---

### 6.4 requirement 类型

**检索场景**："X 的指标要求是什么"、"满足什么条件才合格"、"哪些情况下不需要检测"类查询；
是所有类型中检索频率最高、信息密度最大的类型。

**增强提示词核心逻辑**（requirement_enhance.j2）：
```
提取该文档节中的规范性要求，输出：
- summary：描述本节规范的是什么对象的什么属性，包含哪些维度的要求（若有等级/分类，说明有几个维度）
- keywords：包含所有被约束的属性/指标名称、所有维度分类名称（等级/类型等）、
  出现的关键数值（含单位）、引用的测试方法标准编号
- main_idea：本节最核心的一条要求（一句话）
- questions：{{ questions_count }} 条，优先覆盖：
  "X 在 Y 条件下的要求是什么"、"满足什么条件才能达到 Z 等级"、
  "哪些情况下 X 不需要考核"

附加字段 atomic_propositions（★核心）：
将本节中每个"指标 × 条件/维度"组合，提取为一条独立的、自包含的命题。
命题格式：[主体][条件/等级][属性][关系符][数值]，并附上检测依据（若有）。
若存在例外/豁免条件，在对应命题末尾追加说明。
命题必须覆盖本节内所有规范性要求，不得遗漏任何维度组合。
```

**关于视觉内容**：requirement 节通常包含表格（`tbl≥1`），body_text 中已包含表格 HTML。
增强时应基于表格的行列结构提取 atomic_propositions，每行对应一个指标，每列对应一个等级/条件。

---

### 6.5 procedure 类型

**检索场景**："如何做 X"、"X 的操作步骤是什么"、"X 需要用到哪些设备/试剂"类查询

**增强提示词核心逻辑**（procedure_enhance.j2）：
```
提取该文档节描述的操作过程，输出：
- summary：说明本节描述的是什么操作、操作目的、操作的前提条件和产出结果
- keywords：包含操作名称、所用设备/工具/试剂名称、关键数值参数（温度/时间/压力/速度等+单位）、
  操作动词（核心动作词）
- main_idea：本操作流程最关键的一个步骤或核心参数（一句话）
- questions：{{ questions_count }} 条，覆盖：
  "X 操作的完整步骤是什么"、"X 操作需要哪些设备"、"X 操作的关键参数是什么"、
  "X 操作之后如何处理结果"

附加字段 procedure_summary（结构化提取）：
- operation_name：操作名称
- prerequisites：前提条件（所需设备、材料、样品准备要求）
- key_parameters：关键参数列表（参数名 + 数值 + 单位）
- steps：步骤列表（保留序号，每步一条，不合并）
- output：本操作的产出/结果形式
```

---

### 6.6 evaluation 类型

**检索场景**："达到 X 级需要满足什么条件"、"判定合格的依据是什么"、"检测结果 Y 对应什么等级"类查询

**增强提示词核心逻辑**（evaluation_enhance.j2）：
```
提取该文档节中的评定/判断规则，输出：
- summary：说明本节是对什么的评定（对象）、按照什么维度分级（分级体系）、
  有哪些等级或通过/不通过条件
- keywords：评定对象名称、等级名称、判定阈值（关键数值+单位）、判定条件描述词
- main_idea：最高等级或最严格通过条件（一句话）
- questions：{{ questions_count }} 条，覆盖：
  "X 判定为合格/通过需要满足什么条件"、"测量值为 Y 时属于哪个等级"、
  "有几个等级，各等级如何界定"

附加字段 grade_entries（逐级提取）：
每个等级/判定结论一条记录：
- grade_name：等级/结论名称
- criteria：达到该等级/结论需满足的条件（完整、精确）
- note：备注（若有）
```

---

### 6.7 reference 类型

**检索场景**："本文件引用了哪些外部标准"、"X 指标的测试依据是哪个标准"类查询
**增强动作**：minimal（仅提取 keywords 和 summary，不做深度增强）

**增强提示词核心逻辑**（section_summary.j2 复用）：
```
提取本节引用的外部知识源，输出：
- summary：说明本节共引用了多少个外部文件，主要涉及哪些领域或类别
- keywords：所有被引用文件的编号/名称（这是本节最核心的检索信息）
```

---

### 6.8 narrative 类型

**检索场景**：背景理解、技术原理解释、"为什么这样规定"、补充说明类查询

**增强提示词核心逻辑**（narrative_enhance.j2 / section_summary.j2）：
```
提取该文档节的核心论点或主要说明内容，输出：
- summary：概括本节陈述的背景、原理、动机或补充说明（{{ summary_min }}-{{ summary_max }} 字）
- keywords：核心概念词、关键主张、涉及的实体
- main_idea：本节最重要的一个论点或说明（一句话）
- questions：{{ questions_count }} 条，覆盖"为什么"、"背景是什么"、"原理是什么"类查询
```

## 8. schema.py 扩展：新增字段

基于 9 种通用类型，为各 enhance 类型新增结构化输出 Model（继承 SectionEnhanceModel，不破坏现有 pipeline 校验）：

```python
# schema.py 新增 —— 与 9 种通用 section_type 对齐

# ── meta 类型 ──────────────────────────────────────────────────
class RevisionItem(BaseModel):
    """版本变化条目。"""
    description: str

class DocMetadata(BaseModel):
    """文档身份与溯源信息（meta 类型核心字段）。"""
    doc_id: str = ""
    publish_date: str = ""
    effective_date: str = ""
    responsible_orgs: list[str] = []
    supersedes: str = ""
    revision_summary: list[RevisionItem] = []

class MetaEnhanceModel(SectionEnhanceModel):
    doc_metadata: DocMetadata = None   # type: ignore

# ── scope 类型 ─────────────────────────────────────────────────
class ScopeEnhanceModel(SectionEnhanceModel):
    applicable_to: str = ""    # 适用对象与条件
    excluded: str = ""         # 明确排除的情形（无则填"未作明确排除"）

# ── concept 类型 ───────────────────────────────────────────────
class TermEntry(BaseModel):
    """术语/定义条目（concept 类型用）。"""
    term: str
    definition: str
    notes: str = ""
    aliases: list[str] = []
    related_terms: list[str] = []

class ConceptEnhanceModel(SectionEnhanceModel):
    term_entries: list[TermEntry] = []

# ── requirement 类型 ───────────────────────────────────────────
class AtomicProposition(BaseModel):
    """要求节中每个"指标×条件"组合的原子命题（requirement 类型核心字段）。"""
    text: str   # 自包含命题：[主体][条件/等级][属性][关系符][数值]，附检测依据和例外条件

class RequirementEnhanceModel(SectionEnhanceModel):
    atomic_propositions: list[AtomicProposition] = []

# ── procedure 类型 ─────────────────────────────────────────────
class ProcedureStep(BaseModel):
    seq: int
    text: str

class ProcedureSummary(BaseModel):
    """操作流程结构化提取（procedure 类型核心字段）。"""
    operation_name: str = ""
    prerequisites: str = ""
    key_parameters: list[str] = []
    steps: list[ProcedureStep] = []
    output: str = ""

class ProcedureEnhanceModel(SectionEnhanceModel):
    procedure_summary: ProcedureSummary = None   # type: ignore

# ── evaluation 类型 ────────────────────────────────────────────
class GradeEntry(BaseModel):
    """评定等级/判定结论条目（evaluation 类型核心字段）。"""
    grade_name: str
    criteria: str
    note: str = ""

class EvaluationEnhanceModel(SectionEnhanceModel):
    grade_entries: list[GradeEntry] = []

# ── EnhanceUnit 新增字段 ───────────────────────────────────────
# @dataclass EnhanceUnit 新增（在 schema.py 中更新）：
#   section_type: str = "narrative"     # Stage 2 LLM 输出，9 种之一
#   enhance_guidance: str = ""          # Stage 2 LLM 写入的增强指导意见
#   image_count: int = 0               # BlockIndexer 统计
#   table_count: int = 0               # BlockIndexer 统计
```

**与旧版的关键差异**：
- 去掉领域专用 ExemptionItem、FormulaEntry 等纺织特有字段
- AtomicProposition 简化为单一 `text` 字段（自包含命题，不再拆分子字段）
- TermEntry 去掉 `is_standard_name`/`canonical_name`（由 notes 字段表达即可）
- 每个 EnhanceModel 继承 SectionEnhanceModel，ValidateStage 现有逻辑兼容

## 9. 问答覆盖率验证

基于上述方案，对 175 条问答进行覆盖率分析：

| 问题类型 | 数量 | 覆盖 section_type | 关键增强字段 | 预期覆盖率 |
|---------|------|-----------------|------------|----------|
| 指标阈值查询 | 74 | `requirement` | `atomic_propositions` | **100%** |
| 豁免/不考核 | 14 | `requirement` | `atomic_propositions`（每条命题追加例外条件） | **100%** |
| 试验步骤 | 44 | `procedure` | `procedure_summary.steps` | **100%** |
| 术语定义 | 26 | `concept` | `term_entries` + notes 字段 | **100%** |
| 适用范围 | 10 | `scope` | `applicable_to` + `excluded` | **100%** |
| 元信息/版本 | 7 | `meta` | `doc_metadata` + `revision_summary` | **100%** |
| 判定规则 | 4 | `evaluation` | `grade_entries` | **100%** |
| 跨标准比较 | 4 | 多文档联合 | `keywords`（统一指标名）| 80% |

**关键风险点**（需在检索端补充）：
- **跨标准比较**（Q105-112）：需要多文档同时召回，单文档增强无法完全解决，需在检索层做跨文档聚合
- **CMA能力表**（Q28-30、Q69-71）：这些问题指向内部能力表，非标准文档范围，需要额外数据源

## 10. RAG 检索端建议（超出增强范围，供参考）

### 10.1 混合检索策略

```
query → [BM25 (keyword) + BGE-large-zh (dense)] → RRF 融合排序 → Reranker → Top-K chunks
```

- BM25 对标准编号、指标名称精确匹配效果好（GB/T 3921、耐皂洗色牢度等）
- Dense retrieval 对语义查询效果好（"哪些情况下不考核？"）
- Reranker（cross-encoder）解决 false positives

### 10.2 Metadata 过滤

每个 section 存储以下 metadata，支持精确过滤：
```json
{
  "standard_number": "FZ/T 73020-2019",
  "section_type": "requirement",
  "page_range": [5, 8]
}
```

### 10.3 原子命题独立索引

`atomic_propositions` 中的每条命题作为**独立 chunk** 入库（与完整 section 并列），当查询为精确阈值查询时优先召回原子命题，在答案生成阶段再回溯完整 section 获取上下文。

## 11. 关键设计决策

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 技术要求表格是否拆分 | ❌ 绝不拆分（归入 requirement 节） | 等级比较查询（42%）需要同一节内有全部等级数据 |
| 豁免条款如何处理 | 嵌入同一 requirement section，atomic_propositions 追加例外条件 | 通用方案，无需额外领域专用类型 |
| section_type 体系 | 9 种通用类型（以增强策略差异化为标准） | 覆盖所有文档类型，不绑定纺织领域 |
| atomic_propositions 是否必填 | ✅ requirement 类型必填 | 75% 的阈值查询需要精确匹配指标×等级×数值 |
| evaluation 与 requirement 是否合并 | ❌ 保持独立 | 命题语义形状不同：约束阈值 vs 分类映射；查询方向相反 |
| narrative 类型 | 与 _default 共用 section_summary.j2 | 策略完全相同，无需独立模板 |
| 新增字段与现有 schema 兼容 | 扩展子类 | XxxEnhanceModel 继承 SectionEnhanceModel，不破坏 ValidateStage |
| meta 增强动作 | enhance（非 minimal） | 有 doc_metadata 结构化字段，QA 中 11 条依赖它 |
